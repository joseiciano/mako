# Story 7.10: Interview Booking Channel Compatibility Expansion

**Milestone**: Milestone 7: Interviewer Verification & Premium Matching
**Description**: Add the `interviews.booking_channel` channel discriminator as a **backward-compatible, first-deployment expansion** that adds a **nullable** column plus CHECK constraint, backfills every existing row, and updates every AI/matcher writer plus every read/parser/mapper with a transitional fallback so older and newer Workers coexist. The column is intentionally **not** set `NOT NULL` in this ticket; the contraction to `NOT NULL` is owned by Story 7.11 after the old Workers are deployed and drained.
**Status**: Todo

## What Needs to Be Done

### 1. Add the `booking_channel` column (nullable, backward-compatible)
- [ ] Create a versioned raw SQL migration in `packages/shared-backend/migrations/*.sql` using the workflow in `docs/system/system-design/db-schemas.md` (`pnpm db:migration:create -- interviews_booking_channel`), placed after the migrations that establish the `interviews` table.
- [ ] Add `booking_channel TEXT` to the `interviews` table as **nullable** with **no database default**. This is the backward-compatible first deployment; the column must be capable of holding `NULL` during the transition window so old Workers that have not yet been updated can continue to insert rows.
- [ ] Add a CHECK constraint on `booking_channel` allowing exactly `ai_direct`, `standard_match`, and `verified_interviewer`. The CHECK must permit `NULL` (a nullable column with a CHECK that only constrains non-null values); do **not** set the column `NOT NULL` in this ticket.
- [ ] Do **not** set `booking_channel` to `NOT NULL` in this migration. Contraction to `NOT NULL` is deferred to Story 7.11, which re-backfills gap rows, verifies zero nulls, and only then sets `NOT NULL`.
- [ ] **No backfill in the migration**: this migration adds **only** the nullable column and the CHECK constraint. It performs **no** `UPDATE` backfill of existing rows. The full backfill is moved to a post-deploy resumable bounded-batch script/job (section 2) so the schema change and the data backfill deploy as separate, individually safe steps without a long, unbounded `UPDATE` holding locks during the migration.

### 2. Backfill every existing row via a post-deploy resumable bounded batch (not in the migration)
- [ ] Run the full backfill as a **post-deploy resumable bounded-batch script/job**, not inside the migration and not as one unbounded `UPDATE`. It must be production-safe on a mixed fleet (old Workers that omit `booking_channel` may still be inserting rows while it runs) and must be able to pause and resume.
- [ ] **Bounded small transactions**: process rows in small, bounded batches, each in its own short transaction, using the deterministic rule — rows with `mode = 'ai_led'` become `ai_direct`; rows with `mode = 'peer_to_peer'` become `standard_match` **regardless of whether `interviewer_id` is null** (so legacy matcher-created rows with a null `interviewer_id` — scheduler-initiated peer-to-peer records — are also backfilled to `standard_match`).
- [ ] **Repeated full sweeps, no monotonic cursor**: because this runs on a mixed fleet (older Workers that omit `booking_channel` may still be inserting rows while it runs), the backfill **cannot rely on a monotonic cursor/keyset over random UUID `id` values** — new rows inserted by old Workers can appear ahead of the cursor and be skipped. Instead, require **repeated sweeps from the beginning**, each sweep scanning `WHERE booking_channel IS NULL ORDER BY id` with a configurable `LIMIT` batch size, processing every eligible `NULL` row it sees; batches must be resumable across process restarts by simply starting a fresh sweep.
- [ ] **Configurable batch size and timeouts**: expose a configurable batch size (default a conservative value such as 1,000 rows per transaction) and set `lock_timeout` / `statement_timeout` on each batch statement so a stuck batch aborts safely instead of blocking writes for long.
- [ ] **Metrics/resume**: emit per-batch metrics (rows processed, nulls remaining, batch time) and treat "run is done" as a completed sweep over `WHERE booking_channel IS NULL` (no nulls found), not as the advance of a persisted cursor; re-sweeping already-populated rows is a no-op because the predicate only selects null rows, so a repeated sweep never requires re-processing non-null rows.
- [ ] **Mixed-fleet safe**: the batch only touches rows where `booking_channel IS NULL`, so rows inserted by an older Worker during the drain window are still picked up by a later sweep; the column remains nullable throughout this ticket, so the backfill never blocks older inserters.
- [ ] **No completion claim in this ticket**: because old Workers can keep inserting null rows throughout the drain window, this ticket does **not** claim the backfill is complete. Zero-null completion is only asserted by Story 7.11's post-drain zero-null gate after old Workers are drained.
- [ ] Add a batch-script test asserting the backfill rule: a legacy `peer_to_peer` row with a null `interviewer_id` is backfilled to `standard_match`, and `ai_led` rows are backfilled to `ai_direct`, and that a batch run leaves no eligible `NULL` row unprocessed.

### 3. Update every AI/matcher interview writer (same deploy unit)
- [ ] Update **all existing interview writers** so no writer omits `booking_channel` after this deployment:
  - [ ] AI-direct creation path (`POST /api/interviews`, `mode = 'ai_led'`): set `booking_channel = 'ai_direct'` on insert.
  - [ ] Standard matcher writer (the Greedy Matcher creating `mode = 'peer_to_peer'` sessions): set `booking_channel = 'standard_match'` on insert.
- [ ] Ensure these two writers are deployed **together** in the same release unit that ships this migration, so no updated writer leaves the column unset.

### 4. Update every read / row parser / mapper with a transitional fallback
- [ ] Update the persisted row schema and row parser in `packages/shared-backend/src/database/` so `booking_channel` is carried on every `SELECT` of `interviews`. The persisted row field is `TEXT | null`.
- [ ] Add a **transitional fallback** for null rows: when a row parser or mapper encounters a `NULL` `booking_channel` (rows inserted by an older Worker still running during the drain window, or any other gap row), it must map the value deterministically from `mode` — `mode = 'ai_led'` → `ai_direct`; `mode = 'peer_to_peer'` → `standard_match` — so downstream contracts always see a valid channel even while the column is still nullable.
- [ ] Apply the same transitional fallback in every mapper that reads `interviews` rows before producing a contract (interview list, interview detail, participant payloads, and any notification payload construction).
- [ ] Document the transitional fallback in the row schema/parser module so it is removed together with the `NOT NULL` contraction in Story 7.11.

### 5. Update the shared API contracts and examples
- [ ] Add `booking_channel: 'ai_direct' | 'standard_match' | 'verified_interviewer'` to the shared `Interview`, `InterviewListItem`, and `InterviewDetail` contracts in `packages/shared/src/interviews.ts`, preserving the existing snake_case interview API convention.
- [ ] The public API contracts expose `booking_channel` as a **required non-null** field (the API surface is defined as always carrying the channel, even though the persisted column is transiently nullable and the transitional fallback guarantees the value). Document that the API contract is non-null and the DB nullability is an internal deployment detail resolved by the fallback.
- [ ] Update API documentation/examples (`docs/system/system-design/api-routes.md`) so every `interviews` response example includes `booking_channel`.
- [ ] Export the updated contracts through `packages/shared/src/index.ts` for backend and frontend consumers.

### 6. Notification payload compatibility (transitional ingress parser vs normalized canonical contract)
- [ ] Distinguish **two layers** in the notification pipeline: a **transitional ingress/persisted-event parser** (parses raw outbox/queue envelopes as they arrive, including payloads written by older producers or already persisted before this rollout) and a **normalized canonical event contract** (the typed, validated event variants consumed downstream by orchestrator/consumer logic).
- [ ] **Ingress accepts missing during rollout and derives it from `mode`**: the transitional ingress/persisted-event parser must accept a raw envelope whose `interview` object **omits `booking_channel`** — mixed-fleet producers and already-persisted outbox payloads may omit it — and deterministically **derive** it from the `interview.mode` field: `mode = 'ai_led'` → `ai_direct`; `mode = 'peer_to_peer'` → `standard_match`. A missing `booking_channel` must **never** invalidate, ack-without-processing, or drop the event; the parser supplies the derived value so the event still reaches normalization.
- [ ] **Downstream normalized event variants require non-null channel**: after the transitional ingress parser derives `booking_channel`, the **normalized canonical event contract** in `packages/shared-backend/src/notification-queue-event-contract.ts` and every downstream event variant that carries interview data (e.g. `interview.created`, `interview.cancelled`, matcher-scoped `interview.match.created`) treats `interview.booking_channel` as a **required non-null** field. Only the normalized, validated variants carry this guarantee; the raw persisted outbox/queue payload does not.
- [ ] Keep the canonical snake_case envelope unchanged: every normalized event variant continues to emit the canonical snake_case envelope and includes the derived non-null `interview.booking_channel`.
- [ ] **No invalid-event ack/drop on a missing legacy field**: the ingress parser must **not** classify a legacy envelope with an omitted `booking_channel` as invalid, ack-without-processing, or drop it. Missing `booking_channel` is a supported transitional state resolved by the `mode`-derived fallback, so every event still reaches normalization and downstream handling. In 7.10 this fallback is always present.
- [ ] Add notification **parser and builder** tests across **every existing event variant**: the parser test asserts, for each variant, that a raw envelope with a **missing legacy `interview.booking_channel`** (and a valid `mode`) still parses, derives the correct non-null channel, and produces a normalized event that is **not** acked/dropped as invalid; the builder test asserts every updated event variant emits `interview.booking_channel` as required/non-null in the normalized contract.

## Implementation Notes
- **Prerequisites**: the `interviews` table and Better Auth schema from Milestone 1, the Milestone 2 AI-direct `POST /api/interviews` path, and the Milestone 2 Standard matcher writer.
- `booking_channel` is a channel discriminator and is intentionally separate from `tier`. `tier` continues to encode the payment-policy label (`standard`/`premium`); it is not a channel value.
- This is the **first deployment** of the channel discriminator. It must remain fully backward-compatible: the column is nullable with a CHECK and no default, every existing row is backfilled by a post-deploy bounded batch, every writer is updated, and every reader/mapper has a transitional fallback for null rows so a mixed fleet of old/new Workers produces valid contracts.
- **Deploy/drain requirement for the contraction**: before Story 7.11 may set `booking_channel` to `NOT NULL`, this ticket's release must be fully deployed and old Workers drained (no previously-released Worker version that omits `booking_channel` may still be serving writes). Story 7.11 owns the explicit drain-verification step.
- This ticket does **not** create the premium tables (`premium_interviewer_slots`, `premium_slot_claims`, `premium_booking_credit_refunds`), does not set `NOT NULL`, and does not create any `verified_interviewer` write path. Story 7.11 owns the premium **persistence only** (tables, contracts, and the `NOT NULL` contraction); the production `verified_interviewer` writer is Story 7.15's claim transaction.
- `verified_interviewer` remains a permitted CHECK value but no production write path creates it in this ticket; the claim transaction that creates it is Story 7.15.

## End Goal
Every `interviews` row — new and legacy — reliably carries a valid `booking_channel` (backfilled or written by an updated writer), and every read/parser/mapper and notification payload resolves a valid channel via a transitional fallback even while the column is still nullable. The transitional notification-ingress parser accepts legacy outbox/queue payloads that omit `interview.booking_channel`, derives it from `mode` without acking/dropping events, and normalizes them into canonical event variants that require a non-null channel. The deployment is backward-compatible and safe to roll out alongside older Workers, leaving the `NOT NULL` contraction to Story 7.11.
