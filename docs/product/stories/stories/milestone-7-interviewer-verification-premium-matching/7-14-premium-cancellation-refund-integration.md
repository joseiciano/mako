# Story 7.14: Premium Cancellation & Refund Integration

**Milestone**: Milestone 7: Interviewer Verification & Premium Matching
**Description**: Implement the shared cancellation transaction for `booking_channel = 'verified_interviewer'` interviews and route its **only** two production callers through it: the existing participant cancel route (`POST /api/interviews/:id/cancel`) and the account-deletion workflow (`AccountService.deleteAccount`). It enforces the exact refund rule (scheduler cancellation/deletion → no refund; interviewer cancellation/deletion → exactly one credit refund plus one `premium_booking_credit_refunds` row), writes the existing `interview.cancelled` outbox event atomically on the first `scheduled -> cancelled` transition, and never reopens a claimed slot. No admin route, admin/system sources, or speculative system service are added.
**Status**: Completed

## What Needs to Be Done

### 1. Shared cancellation transaction (exact semantics)
- [x] Build **one** shared cancellation transaction used by **all** cancellation callers in this ticket (participant cancel route and account deletion). Do not create a second cancellation path or keep the direct bulk update as an alternative.
- [x] The transaction attributes a `source` of exactly `scheduler` or `interviewer`:
  - [x] Participant cancel route: infer `scheduler` when the acting participant is the interview's `scheduler_id`, and `interviewer` when the acting participant is the `interviewer_id`.
  - [x] Account deletion: if the deleted user is the interview's `scheduler_id`, treat as source `scheduler`; if the deleted user is the `interviewer_id`, treat as source `interviewer` with refund reason `interviewer_account_deleted`.
- [x] Use the exact deterministic participant locking protocol before any mutation: inside the transaction, lock the affected participant `"user"` rows **in UUID order (`ORDER BY id`)** with `SELECT ... FOR UPDATE`, so cancellation serializes against concurrent claims and other cancellations. Re-check interview state after acquiring the locks; do not trust pre-transaction state.
- [x] **Refund rule on the first `scheduled -> cancelled` transition**, atomically within the transaction:
  - [x] Source `scheduler` (participant cancel or account deletion): **no refund**; no `premium_booking_credit_refunds` row; the scheduler-initiated cancellation consumes the paid credit.
  - [x] Source `interviewer` via participant cancel: insert **exactly one** `premium_booking_credit_refunds` row with `reason = 'interviewer_cancelled'`, `initiated_by_user_id` = the cancelling interviewer, `credits_refunded = 1`, `created_at`, and increment the scheduler's credit by one (raw SQL `UPDATE "user" SET credits = credits + 1` guarded appropriately) in the same transaction.
  - [x] Source `interviewer` via account deletion: insert **exactly one** `premium_booking_credit_refunds` row with `reason = 'interviewer_account_deleted'`, `initiated_by_user_id` = the deleting interviewer's user ID (non-null; the account-deletion workflow attributes the refund to the deleted interviewer), `credits_refunded = 1`, `created_at`, and increment the scheduler's credit by one in the same transaction.
- [x] The `premium_booking_credit_refunds` ledger created by Story 7.11 already restricts `reason` to `interviewer_cancelled | interviewer_account_deleted` and requires `initiated_by_user_id` non-null (the acting interviewer for `interviewer_cancelled` and the deleting interviewer's ID for `interviewer_account_deleted`). No migration or amendment of those CHECK constraints is needed; do not add any amend/alter-current-old-values language. The unique `interview_id` on the ledger remains the backstop preventing a double refund row.
- [x] **Outbox event**: on the first `scheduled -> cancelled` transition write exactly **one** existing `interview.cancelled` outbox event atomically within the same transaction (the existing Milestone 2 outbox pattern), carrying the canonical cancellation envelope for the interview. A `cancelled -> cancelled` retry returns success with **no** second refund row, **no** second credit increment, and **no** second outbox event (Milestone 2 cancel idempotency).
- [x] **Producer ownership**: update the existing Milestone 2 `interview.cancelled` producer ownership so **both** production callers here — the participant cancel route **and** the account-deletion shared cancellation transaction — may produce the event, each only on the first `scheduled -> cancelled` transition. No other caller may emit it; a retry never re-emits it.
- [x] Never automatically reopen a `claimed` premium slot on any cancellation: the slot stays `claimed` (or is left in its persisted state) and never returns to the marketplace as `available`.
- [x] Do not record any `stripe_payment_intent_id`-keyed ledger entry; `Credit_Transactions` is the Stripe fulfillment ledger and `premium_booking_credit_refunds` is the separate internal audit/idempotency ledger (see `docs/system/system-design/db-schemas.md`). Document this distinction.

### 2. Route the existing participant cancel route through the shared transaction
- [x] Rework the existing `POST /api/interviews/:id/cancel` (Milestone 2) for `booking_channel = 'verified_interviewer'` interviews so it calls the shared cancellation transaction with the inferred `scheduler`/`interviewer` source. Non-premium interviews keep their existing cancellation behavior unchanged.
- [x] Define the exact status/auth/error behavior for this route (unchanged surface, exact mappings):
  - [x] `400`: malformed/missing interview `id`. This route has **no request body**, so no body-related `400` exists.
  - [x] `401`: unauthenticated request.
  - [x] `404`: the interview does not exist or the authenticated user is not a participant (do not leak existence).
  - [x] `409`: the interview is in a non-cancellable state (e.g. already started/`ongoing`), i.e. "only scheduled interviews can be cancelled".
  - [x] `200`: successful `scheduled -> cancelled` transition, and also the idempotent `cancelled -> cancelled` retry.
- [x] Remove any reliance on the deleted admin route/`requireAdmin`; the participant route requires no admin authorization.

### 3. Integrate account deletion (no partial success, shared protocol)
- [x] Replace `AccountRepository.cancelUpcomingInterviews` (the direct bulk `UPDATE interviews SET status = 'cancelled' ...`) with the shared cancellation transaction so account deletion honors refund/outbox semantics. The replacement must **preserve cancellation of AI and Standard interviews** (the existing Milestone 2/4/6 deletion behavior for non-premium interviews is unchanged), and must emit **one `interview.cancelled` outbox event for every first `scheduled -> cancelled` transition across all channels** — AI, Standard, and verified. Only `booking_channel = 'verified_interviewer'` interviews enter the refund/refund-row path; AI/Standard cancellations produce no refund and no refund ledger row.
- [x] **Premium refund applies only to the verified channel**: only `booking_channel = 'verified_interviewer'` interviews may produce a `premium_booking_credit_refunds` row and a one-credit increment; AI/Standard cancellations never refund a credit and never write a refund row.
- [x] **Global multi-interview lock protocol** for account deletion (the deterministic protocol that serializes the whole deletion against concurrent claims/cancellations and never partially applies):
   1. **Snapshot the affected participant IDs**: collect the distinct participant user IDs (`scheduler_id` / `interviewer_id`) across all upcoming interviews being cancelled by the deletion, and **always include the deleting account's user ID in the initial lock union** (even if it is not currently a participant in any affected interview), so the deleting user's own row is locked from the start.
   2. **Lock the union once in UUID order**: within the single transaction, `SELECT id FROM "user" WHERE id = ANY($snapshot) ORDER BY id FOR UPDATE` — one pass locking every affected participant user row (including the deleting account) in deterministic `id` (UUID) order.
   3. **Re-read/lock the interviews by ID**: after acquiring the user locks, **re-query all qualifying interviews for the deleting account** (re-select the interviews to cancel by the deleting user's id/participant role rather than trusting only the pre-lock snapshot IDs), then `SELECT ... FOR UPDATE` those affected `interviews` rows by `id` and re-check each one's current participant set and `status` against the snapshot (do not trust pre-transaction state).
   4. **Rollback/retry if the interview or participant union expands**: if a re-read reveals an interview not in the original snapshot, or any locked interview references a participant who is not in the originally snapshot set (e.g. a concurrent claim reassigned or added a participant), roll back the transaction, retake the new **expanded** snapshot (expanded interview set and participant union) in UUID order, and retry — never mutate on a stale snapshot.
  5. **Then mutate**: only after the union lock is stable and all affected interviews are re-locked by ID and revalidated, apply cancellations + outbox writes for **every** affected interview on its first `scheduled -> cancelled` transition (across AI, Standard, and verified channels), and apply (verified-channel only) refunds/refund-rows.
- [x] Account deletion must **not return success with partial cancellation/refund/outbox cleanup**: for each affected `booking_channel = 'verified_interviewer'` interview, the cancellation + any refund + refund-row insert + outbox write must commit atomically, and any failure rolls back so `deleteAccount` surfaces the failure (never a partial success).
- [x] Account deletion is **all-or-nothing** across the premium cancellation/refund/outbox work **and** the account soft-deletion itself: if any affected premium interview cannot be cleanly cancelled/refunded, the deletion workflow aborts and the account is left **active** (not partially deleted) with no refund/outbox side effects persisted. Run all of this work in **one** transaction or an equivalent repository boundary, and guard it with the same race-safe deterministic locks (participant user-row locks in UUID order, and any needed account/idempotency locks) so a concurrent claim/cancellation cannot interleave and produce a partially deleted account.
- [x] Use the same deterministic participant locking protocol as the participant route so account deletion serializes against concurrent claims/cancellations; account deletion must not reopen claimed slots or double-refund under races.
- [x] Define internal account-deletion failure/rollback behavior: if the shared cancellation transaction fails for any affected interview, the deletion workflow aborts with a deterministic error and no partial refund/outbox side effects are persisted; no `success: true` is returned until every affected premium interview is cleanly cancelled/refunded or confirmed already handled.

## Implementation Notes
- **Prerequisites**: Story 7.10/7.11 (persistence + shared contracts + the `premium_booking_credit_refunds` ledger), the Milestone 2 cancel route and `interview.cancelled` outbox pattern, and Milestone 6 credit repository (`creditRepository`).
- The scheduler pays exactly one credit; a scheduler-initiated cancellation consumes it (no refund). Only interviewer-initiated cancellation or interviewer account deletion refunds exactly one credit.
- The shared transaction is the single cancellation path for `verified_interviewer` bookings; `AccountRepository.cancelUpcomingInterviews`'s direct bulk update is removed.
- Cancellation here only handles interview-level cancellation/refund/outbox. Slot status semantics are owned by Story 7.15 (claim) and Story 7.12 (publish/cancel-slot); this ticket only guarantees a claimed slot is never reopened by cancellation.
- No interviewer charge, compensation, or payout occurs anywhere in the cancel/refund flow.
- Do not update the public discovery/claim API in this ticket; Story 7.15 references this cancellation behavior but implements the booking surface.

## End Goal
Cancelling a `booking_channel = 'verified_interviewer'` interview — by a participant or via account deletion — flows through one shared transaction that atomically cancels the interview, writes the existing `interview.cancelled` outbox event on the first `scheduled -> cancelled` transition, and applies the exact refund rule (no refund on scheduler-initiated cancellation/deletion; exactly one credit refund and one `premium_booking_credit_refunds` row on interviewer cancellation/deletion). Retries never double-refund or double-dispatch, claimed slots are never reopened, account deletion never returns partial success, and no admin route or speculative system service exists.
