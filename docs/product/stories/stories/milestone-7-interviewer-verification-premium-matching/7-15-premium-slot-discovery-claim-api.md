# Story 7.15: Premium Slot Discovery & Claim API

**Milestone**: Milestone 7: Interviewer Verification & Premium Matching
**Description**: Implement the public first-to-claim premium marketplace discovery listing and the atomic scheduler claim transaction that, in one database transaction, revalidates eligibility/conflicts, deducts exactly one scheduler credit, creates the `booking_channel = 'verified_interviewer'` interview, claims the slot, and writes the `interview.premium_booked` notification-outbox event — deduplicated by a UUID `Idempotency-Key`, with the exact deterministic lock order and the cross-channel overlap protocol. Cancellation/refund behavior is referenced but **not** implemented here (it is owned by Story 7.14).
**Status**: Completed

## What Needs to Be Done

### 1. Marketplace discovery (public listing)
- [ ] Implement `GET /api/premium/marketplace` (the route locked by Story 7.11) with optional `interviewType`, `limit`, and `offset` query parameters. Return only `available` slots inside the currently claimable policy window (`start_time >= now + lead time` and `start_time <= now + horizon`) whose owner is active and still has `"user".companies = true`, ordered deterministically `ORDER BY start_time ASC, id ASC`, with the Story 7.11 pagination defaults (`limit` default 25, max 100, `offset` 0).
- [ ] **Query validation is exact**: `limit` and `offset` must be validated as **non-negative integers** with `limit` in `[1, 100]`; `interviewType` must be one of `system_design | coding | behavioral` if present; invalid values return `400 { error: string }`.
- [ ] This route is explicitly **unauthenticated/public**. Discovery is display-safe and browsable without login. Set `Cache-Control: no-store`.
- [ ] Return exactly the safe public fields: `slotId`, `interviewType`, `startTime`, `endTime`, and an `interviewer` object containing **only** `displayName` (from `"user".name`), `image` (nullable profile image), and `isVerified: true`. Do **not** expose application/employment history, private employment data, reviewer identity, contact email, or any company/role verified claims.
- [ ] Derive `isVerified: true` solely from `"user".companies = true` (the Story 7.8 eligibility flag) on the slot owner; never assert company/role-level verification.
- [ ] **Response envelope is exact**: `{ slots: PremiumMarketplaceSlot[], pagination: { limit: number, offset: number, hasMore: boolean }, policy: PremiumPolicyMetadata }`, where `limit`/`offset` are the validated integers and `policy` reports the active configured lead/horizon values and the fixed `priceCredits: 1`.
- [ ] Return errors with the existing `{ error: string }` shape.
- [ ] Add tests asserting the listing returns only `available` slots, deterministic ordering/pagination, the `policy` metadata, exact integer pagination validation, and that no private field (application, employment, reviewer, contact, company/role claims) appears in the response.

### 2. Abuse control for public discovery (exact decision: Workers Rate Limiting)
- [ ] Protect `GET /api/premium/marketplace` with a **Cloudflare Workers Rate Limiting binding** on this public route, keyed per `CF-Connecting-IP` plus a route key (e.g. `premium:marketplace`), with a default limit of **60 requests per 60 seconds** per Cloudflare location. When exceeded, return exactly `429 { error: 'RATE_LIMITED' }`.
- [ ] Add the rate-limiter binding to the Wrangler config with environment typing (e.g. an `Env` binding typed via `@cloudflare/workers-types`), inject the limiter into the route/handler for testability (a test double injects instead of the real binding), and add route tests asserting the limit window and the exact `429 { error: 'RATE_LIMITED' }` body.
- [ ] Emit **PII-safe rate-limit log events** (derived location hash of the IP + route key + outcome only). **Rate-limit logs must never include the raw `CF-Connecting-IP` (or any full IP address)**; the raw `CF-Connecting-IP` is used only as the limiter key and never written to logs. Never log full request bodies, auth cookies, or other PII. Document the binding, limits, and this route's protection in `docs/system/system-design/api-routes.md` and the Wrangler config docs.
- [ ] Add a rate-limit test asserting the emitted log events contain only the derived location hash/route key/outcome and never the raw `CF-Connecting-IP` value.
- [ ] Treat this limiter as **abuse protection only, not accurate accounting**: it is not a substitute for per-user billing or quota enforcement, and it must not be relied on for precise request counting. No speculative abuse-control service, middleware framework, or new infrastructure is added.

### 3. Claim a slot (atomic transaction with exact lock order)
- [ ] Implement `POST /api/premium/marketplace/slots/:id/claim` (the route locked by Story 7.11), guarded by auth (active, non-deleted scheduler). Unauthenticated → `401`; an authenticated inactive/deleted account → `403 { error: 'ACCOUNT_INACTIVE' }`.
- [ ] Require a UUID `Idempotency-Key` header (validate it is a well-formed UUID; missing/invalid → `400`). This key drives replay/conflict semantics.
- [ ] Reject self-claim with `403`: after loading the slot under the transaction locks below, the authenticated scheduler must not equal the slot's `interviewer_id`.
- [ ] Execute the whole claim in **one** database transaction using the exact lock-first order below. Use raw SQL via Hyperdrive with the shared query executor; no ORM.
- [ ] **Exact lock order** (apply in this deterministic order; all inside the single transaction):
  1. Take a **transaction-scoped advisory lock derived from the `Idempotency-Key`** (e.g. `pg_advisory_xact_lock(hashtext('premium-claim:' || idempotency_key))`) so the same key's concurrent replays serialize.
   2. **Check `premium_slot_claims`** by `idempotency_key`: if an existing row records the **same** `scheduler_id` + `slot_id`, **enforce the active account before replaying**: lock the scheduler `"user"` row (`SELECT ... FOR UPDATE`), verify the scheduler account is active; if inactive/deleted return `403 { error: 'ACCOUNT_INACTIVE' }`; otherwise return `200` with the existing created `InterviewDetail` (idempotent success, no revalidation, no second charge, no second claim, no second outbox write) — this must succeed even after the slot is already `claimed`, but **never** for an inactive/deleted scheduler. If the recorded key maps to a **different** `scheduler_id` or `slot_id`, return `409 { error: 'IDEMPOTENCY_KEY_CONFLICT' }`.
  3. Take an **advisory lock derived from the slot ID** (`pg_advisory_xact_lock(hashtext('premium-slot:' || slot_id))`), then `SELECT ... FOR UPDATE` the `premium_interviewer_slots` row by `id`. **Re-check the claim after the wait**: after acquiring the row lock, re-read `premium_slot_claims` for any existing claim on this slot. If a claim already exists, return `409 { error: 'PREMIUM_SLOT_ALREADY_CLAIMED' }`.
  4. Lock the scheduler and interviewer user rows **in UUID order (`ORDER BY id`)** with `SELECT ... FOR UPDATE` — the same deterministic user-row locks tier-policy and matcher writers use, so cross-channel writes serialize on the same rows. Document that these locks interoperate with the existing tier-policy/matcher user locks.
  5. **Validate/charge/write** (revalidation, credit deduction, interview creation, slot claim, outbox write — see below). Any failure after this point rolls back the entire transaction.
- [ ] **Revalidation at claim** (re-check, never trust publish-time state): an unknown or `cancelled` slot returns `404`; a `claimed` slot returns `409 { error: 'PREMIUM_SLOT_ALREADY_CLAIMED' }`; the scheduler must be active; the interviewer must still be active with `"user".companies = true` or return `409 { error: 'PREMIUM_INTERVIEWER_INELIGIBLE' }`; the window must still satisfy the active lead/horizon policy; and the slot must not conflict with an existing `scheduled`/`ongoing` interview where either participant appears in either role. Use `newStart < (existing.scheduled_at + interval '60 minutes') AND existing.scheduled_at < newEnd`; scheduling or policy-window conflicts return `409 { error: 'PREMIUM_SCHEDULING_CONFLICT' }`. Every failure rolls back with no partial writes.
- [ ] **Credit deduction**: deduct exactly **one** scheduler credit via `creditRepository.decrementCredits()` (from Story 6.2) using the shared transaction executor — the free-Standard quota **never** applies and is never consumed for verified-interviewer bookings. Insufficient balance returns `409 { error: 'INSUFFICIENT_CREDITS' }` and full rollback.
- [ ] **Interview creation**: insert one `interviews` row with `mode = 'peer_to_peer'`, `booking_channel = 'verified_interviewer'`, `type` from the slot's `interview_type`, `status = 'scheduled'`, `scheduled_at` = slot `start_time`, `scheduler_id` = claimant, `interviewer_id` = slot `interviewer_id`, `tier = 'premium'` (payment-policy outcome of the single credit), and alias fields per the shared alias policy used by Milestone 2.
- [ ] **Slot claim**: transition the slot to `status = 'claimed'` atomically within the same transaction. A claimed slot must **never** return to `available`.
- [ ] **Claim store**: insert into `premium_slot_claims` with `idempotency_key`, `slot_id`, `scheduler_id`, `interview_id`, and `created_at`.
- [ ] **Response envelope is exact**: the claim returns `{ interview: InterviewDetail }` — the credential-safe interview detail (excludes provision-only `realtime_session_id`, `excalidraw_room_id`, `excalidraw_key`), the created interview on initial claim with `201`, and the same existing `InterviewDetail` on a same-key replay with `200`.
- [ ] Retry retryable transaction conflicts (`40001`, `40P01`) with **bounded** attempts (three total) after rollback; on exhaustion produce a deterministic error/log and do not partially apply any step.

### 4. Notification outbox: `interview.premium_booked`
- [ ] Add a new event literal `interview.premium_booked` to the shared notification event schema/consumer ownership (extend the existing `packages/shared-backend/src/notification-queue-event-contract.ts` and the shared consumer ownership in the notification module). Do **not** reuse the matcher-owned `interview.match.created` event; it stays matcher-scoped. This is the **only** outbox event written by the claim transaction.
- [ ] The `interview.premium_booked` event carries the canonical snake_case notification envelope and interview/participant payload used by existing events, extended with `interview.booking_channel = 'verified_interviewer'`.
- [ ] Use the deterministic idempotency key `premium-booking:{interview_id}` for the outbox event so a retry/dispatch cannot duplicate the event.
- [ ] Write the outbox event atomically within the claim transaction via the existing notification repository outbox pattern (same transaction as credit deduction, interview creation, and slot claim).
- [ ] **Extend the notification consumer to handle `interview.premium_booked` by explicitly mirroring the `interview.match.created` consumer behavior** (the Notification Orchestrator Worker's durable post-commit processing), with the event root `interview.premium_booked`:
  - [ ] **Confirmation to both participants after commit**: after the outbox event commits, the consumer sends a confirmation to **both** participants (the scheduler and the interviewer), keyed by the deterministic per-effect checkpoint `interview.premium_booked:confirmation` and delivery idempotency key `${idempotency_key}/confirmation`, exactly like `interview.match.created`.
  - [ ] **30-minute reminder when eligible**: schedule a reminder `30 minutes before scheduled_at` only while the interview is still `status = 'scheduled'` and the reminder window is valid, gated by the deterministic per-effect checkpoint `interview.premium_booked:reminder`; suppress when the window is past/too-late or the interview is no longer scheduled (mirroring `interview.match.created`).
  - [ ] **Existing reminder suppression on `interview.cancelled`**: the existing `interview.cancelled` consumer suppression path (`interview.cancelled:suppression` checkpoint → `suppressReminderSchedulesForInterview`) must apply to premium bookings, so a cancelled verified-interviewer interview's pending reminder is suppressed by the existing flow (no new suppression mechanism).
  - [ ] **No duplicate confirmation/reminder on replay**: re-processing the same `interview.premium_booked` event is idempotent via the per-effect checkpoints `${root}:confirmation` and `${root}:reminder`; a replay emits no second confirmation or reminder.
- [ ] Update the notification event/transport/confirmation docs — `docs/product/stories/stories/milestone-2-interview-scheduling-dashboard/4-2-notification-event-contract-and-producer-ownership.md` (event contract + consumer ownership), `4-3-notification-transport-reliability-and-idempotency.md` (transport/outbox), and `4-4-confirmation-and-reminder-workflow-rules.md` (confirmation/reminder rules) — and `docs/infrastructure/backend.md` (the Notification Orchestrator Worker section) to list `interview.premium_booked` as a known consumer-owned event with the `:confirmation` / `:reminder` per-effect checkpoints and the mirrored confirmation-to-both + 30-minute reminder behavior.
- [ ] Extend the shared notification event schema and consumer ownership docs so the `interview.premium_booked` event is a known, owned event with defined recipients (the scheduler and the interviewer).
- [ ] Add tests: event dispatch after a successful claim, replay does not produce a second outbox write, and the event reaches the correct recipients with the canonical envelope plus `booking_channel`. Add consumer tests asserting confirmation reaches both participants exactly once, a valid 30-minute reminder is scheduled, reminders are suppressed on `interview.cancelled`, and replay via the `${root}:confirmation` / `${root}:reminder` checkpoints emits no duplicate confirmation/reminder.

## Implementation Notes
- **Prerequisites**: Story 7.11 (persistence + shared contracts + locked routes + `premium_slot_claims`/`premium_interviewer_slots`), Story 7.12 (publish/eligibility + user-row lock protocol), a **production-ready Story 7.14** (the shared cancellation/refund transaction this booking surface relies on), Milestone 6 credit ledger/repository (6-1, 6-2), and Milestone 2 notification outbox (Story 4.2/4.3 pattern) + notification event schema/consumer ownership.
- The scheduler pays exactly one credit; the free-Standard quota is never applied to verified-interviewer bookings. This is a hard rule, not a config fallback.
- The claim is a single all-or-nothing transaction; the exact lock order (idempotency advisory lock → claim-store check → **on same-key replay, lock the scheduler `"user"` row and verify active before returning the replay** → slot advisory lock + `FOR UPDATE` → user-row locks in UUID order → validate/charge/write) is required and deterministic. The deterministic user-row locks reuse the tier-policy/matcher locks to serialize cross-channel writes.
- **Cancellation/refund is referenced but not implemented here.** Cancelling a claimed/created booking (scheduler vs interviewer refund semantics, account-deletion integration, outbox `interview.cancelled`) is owned entirely by Story 7.14. This ticket only guarantees a claimed slot is never reopened and otherwise defers cancellation behavior.
- No interviewer charge, compensation, or payout occurs anywhere in the claim flow.
- The marketplace exposes only display-name/image/verified-badge/type/time/policy; never application/private employment/reviewer/contact fields or company/role verified claims.
- `POST /api/interviews` remains AI-only; the Standard matcher stays unchanged; join-time provisioning (`POST /api/interviews/:id/provision`) is unchanged and still applies to the created premium interview as a participant interview.
- Abuse control for public discovery is a Cloudflare Workers Rate Limiting binding on this route, keyed per `CF-Connecting-IP` plus a route key at 60 requests per 60 seconds per Cloudflare location, returning `429 { error: 'RATE_LIMITED' }`. It is abuse protection only, not accurate accounting; no speculative abuse service is added.

## End Goal
Schedulers can browse a public first-to-claim marketplace of verified-interviewer slots and atomically claim one, paying exactly one credit and creating a `booking_channel = 'verified_interviewer'` interview with the claimant as scheduler and the interviewer fixed — deduplicated by a UUID idempotency key with an exact deterministic lock order, conflict-safe under concurrency, emitting a dedicated `interview.premium_booked` notification with exact query-validation and `{ interview }`/`{ slots, pagination, policy }` response envelopes, while cancellation/refund behavior is defined by the production-ready Story 7.14.
