# Story 7.16: Premium Scheduler Booking Flow

**Milestone**: Milestone 7: Interviewer Verification & Premium Matching
**Description**: Build the scheduler-facing frontend that browses the first-to-claim verified-interviewer marketplace, claims an available slot (paying exactly one credit via the Story 7.15 claim route with a UUID idempotency key), and reflects booking/cancellation outcomes. It presents **only** `system_design` inventory as a third branch inside `/interviews/new`.
**Status**: Todo

## What Needs to Be Done

### 1. Placement and data layer
- [ ] Add a **third branch inside the existing `/interviews/new` flow**: AI direct, Standard P2P availability, or Verified Interviewer. Verified Interviewer is added alongside the existing AI-led and Standard P2P availability options and opens the premium scheduler booking surface.
- [ ] Version the existing `mako:schedule-flow:draft:v1` envelope to **v2** for the new three-branch state using an exact discriminated union, stored under the exact key **`mako:schedule-flow:draft:v2`** in **`localStorage`** so the durable draft survives browser/tab close and reopen. Define the v2 contract as a tagged envelope discriminated by a `branch` field with exactly three **submission** members — `ai_direct`, `standard_p2p`, `verified_interviewer` — plus a `pre_branch` member for the pre-submission UI state. The `pre_branch` variant durably persists **incomplete v1 drafts** (drafts that have not yet selected a submission branch) so no stored draft is lost during the v1→v2 migration. Each submission branch must **losslessly preserve the valid normalized/restorable v1 state** for the AI/P2P paths (the shared v1 AI and P2P draft payloads are carried through with their current normalized/restorable values intact, just re-tagged under `ai_direct` and `standard_p2p` respectively; see the exact v2 envelopes below). The `verified_interviewer` branch is new and must durably persist exactly `{ slotId, idempotencyKey, startedAt }` (ISO-8601 `startedAt`) so a reload/reopen can resume an in-flight claim.
- [ ] **Exact v2 envelopes** (using the current v1 `ScheduleDraftData` property names `step`, `interviewType`, `mode`, `scheduledAt`, `maxMatches`, `slots`; the shapes below match the **current normalized/restorable v1 state**, so any v1 draft that is validly normalized/restored maps losslessly):
  - `pre_branch`: `{ version: 'v2', branch: 'pre_branch', draft: { step, interviewType, mode: null, scheduledAt: null, maxMatches: null, slots: [] } }` — a pre-submission state persisted for **incomplete v1 drafts** that have not yet chosen a submission branch; it **represents the current normalized no-mode state** and is carried through losslessly, only ever advanced to a submission branch when the user actively selects one.
  - `ai_direct`: `{ version: 'v2', branch: 'ai_direct', draft: { step, interviewType, mode: 'ai_led', scheduledAt: ISO-8601 | 'now' | null, maxMatches: null, slots: [] } }` — the full v1 `ScheduleDraftData` payload carried through losslessly per the current v1 normalized/restorable state (`scheduledAt` may be `ISO-8601 | 'now' | null`).
  - `standard_p2p`: `{ version: 'v2', branch: 'standard_p2p', draft: { step, interviewType, mode: 'peer_to_peer', scheduledAt: null, maxMatches: positive integer | null, slots: { startTime: ISO-8601, endTime: ISO-8601 }[] } }` — the full v1 `ScheduleDraftData` payload carried through losslessly per the current v1 normalized/restorable state: `scheduledAt` is **exactly `null`**, `maxMatches` is a **positive integer or `null`**, and the `slots` array **may be incomplete or empty** as accepted by the normalized draft.
  - `verified_interviewer`: `{ version: 'v2', branch: 'verified_interviewer', slotId: UUID, idempotencyKey: UUID, startedAt: ISO-8601 }` — no `draft` object; the branch payload is `{ slotId, idempotencyKey, startedAt }`.
- [ ] **Storage migration order (v1 → v2)**: the v2 key **`mako:schedule-flow:draft:v2` lives in `localStorage`** (durable across browser/tab close), while the legacy v1 key **`mako:schedule-flow:draft:v1` lives in `sessionStorage`** (the pre-M7 location). On restore, **read the v2 `localStorage` key (`mako:schedule-flow:draft:v2`) first**; if the stored value is v2, use it directly. Otherwise **fall back to reading/validating the v1 `sessionStorage` key** (`mako:schedule-flow:draft:v1`), validate it as a v1 `ScheduleDraftData` envelope, and **import/migrate it into the v2 `localStorage` key**: a complete v1 AI/P2P draft maps to its unchanged v2 submission branch (`ai_direct` or `standard_p2p`), while an **incomplete v1 draft** (no submission branch selected yet) maps to the `pre_branch` variant; reject malformed/unknown/missing-`branch` envelopes. On write, always **write v2 to `mako:schedule-flow:draft:v2` in `localStorage`** first and only **remove the v1 `sessionStorage` key after a successful v2 write** (write-before-delete — never delete v1 before v2 is durably persisted). On an interrupted migration (v2 write failed), leave v1 intact so a subsequent restore can retry the read-v1 → write-v2 → remove-v1 sequence; the migration is lossless for AI/P2P and never reinterprets a v1 P2P draft as `verified_interviewer`.
- [ ] Restore valid v1 AI/P2P drafts through an explicit migration that maps them to their unchanged v2 submission branches and incomplete v1 drafts to `pre_branch`; reject malformed/unknown/missing-`branch` envelopes; never reinterpret a v1 P2P draft as `verified_interviewer`. Keep the existing pending-create guard behavior for the `ai_direct` branch and use the `idempotencyKey` for Premium retries.
- [ ] Add scheduler booking hooks/transport in `apps/frontend/src/hooks/use-premium-marketplace.ts` using the Story 7.11 shared contracts and the Story 7.15 routes (`GET /api/premium/marketplace`, `POST /api/premium/marketplace/slots/:id/claim`).
- [ ] Use TanStack Query with a marketplace query key that requests `interviewType=system_design`; invalidate/refetch it after a successful claim so the claimed slot disappears from `available`.
- [ ] Generate a fresh UUID `Idempotency-Key` for each **new logical booking claim** (for example with `crypto.randomUUID()`), retain it through every retry until that claim reaches a terminal success/conflict, and attach it as the header. Generate a new key only when the user starts a genuinely different slot claim.
- [ ] Render only the safe public marketplace fields: display name, optional image, verified badge, `system_design` type, and time window. Never render application/private employment/reviewer/contact fields or any company/role verified claims.

### 2. Browse and booking UI (system_design only)

### 3. Claim interaction and idempotency handling
- [ ] On a booking action, call the claim route with the generated `Idempotency-Key`; show an in-flight "reserving" state and prevent duplicate submission while the mutation is pending.
- [ ] **Persist before claim (synchronous write)**: before issuing any HTTP claim request, the client must **synchronously and successfully persist** the durable claim `{ slotId, idempotencyKey, startedAt }` (to `mako:schedule-flow:draft:v2`, `verified_interviewer` branch) and receive an acknowledgment of that write. If the persistence write throws or fails (e.g. storage unavailable), **do not send the claim request**; surface a recoverable error and keep the claim unsubmitted so a later retry starts from a clean, unsent state. A claim request is only sent after the durable claim is durably stored.
- [ ] Handle success by refetching the marketplace (slot no longer available), clearing the durable draft claim, and navigating/confirming the created booking via the returned interview. Treat the initial `201` and the same-key replay `200` both as success.
- [ ] On `409 { error: 'PREMIUM_SLOT_ALREADY_CLAIMED' }`, invalidate/refetch the marketplace, show that the slot is no longer available, and treat the claim as **terminal after reconciliation**. On `IDEMPOTENCY_KEY_CONFLICT`, stop automatic retries and require a new logical claim/key — with the **same-slot exception**: the user may resubmit the **same slot** by atomically replacing the durable `idempotencyKey` with a fresh UUID and resetting `startedAt` before resubmitting. The conflicting key is never reused.
- [ ] Handle the other exact `409` literals without removing a still-available slot: `INSUFFICIENT_CREDITS` links to the Milestone 6 billing flow; `PREMIUM_SCHEDULING_CONFLICT` explains the participant time conflict; `PREMIUM_INTERVIEWER_INELIGIBLE` invalidates/refetches marketplace inventory. Retain the logical claim and its `idempotencyKey` wherever a retry can still be meaningful.
- [ ] On transient/network failure or an unknown result, allow a retry that reuses the same `Idempotency-Key` so a previously succeeded claim is not double-charged; on `200`/idempotent success reconcile to the created booking.

#### Claim lifecycle rules
Persist the durable `{ slotId, idempotencyKey, startedAt }` claim across reload/reopen and drive state transitions from the server result only. Apply these exact rules:

| Condition / outcome | Rule |
|---|---|
| Network failure or unknown result (lost response) | Retain the logical claim and key. On reload/reopen, replay the **same key** for the **same slot before issuing any new claim**. Never start a fresh key while the prior result is unknown. |
| Success (`201` initial / `200` replay) | Clear the durable claim; reconcile to the created booking. |
| `PREMIUM_SLOT_ALREADY_CLAIMED` | **Terminal** after reconciliation: refetch marketplace, discard the claim and its key. |
| `PREMIUM_INTERVIEWER_INELIGIBLE` | **Terminal** after reconciliation: invalidate/refetch marketplace inventory, discard the claim and its key. |
| `INSUFFICIENT_CREDITS` | Retain the logical claim and key; surface the billing path; allow retry. |
| `PREMIUM_SCHEDULING_CONFLICT` | Retain the logical claim and key; explain the conflict; allow retry on the same slot. |
| `IDEMPOTENCY_KEY_CONFLICT` | Requires a new key; stop automatic retries; do not reuse the conflicting key. **Same-slot exception**: the user may resubmit the **same slot** by atomically replacing the durable key with a fresh UUID and resetting `startedAt`, then resubmit that slot claim with the new key. A key replacement is an explicit user-initiated resubmit, never an automatic retry. |
| User switches to a different slot | Must first reconcile or clear any in-flight/unknown claim. **Never silently abandon an unknown claim**; resolve (replay same key to confirm, or surface the unknown outcome) before starting a new claim with a new key. |

- [ ] For the scheduler's own cancellation of this booking, reflect the no-refund outcome (the scheduler-initiated cancellation does not refund the paid credit).
- [ ] Reflect the refunded-one-credit outcome for the non-scheduler-initiated cancellation outcomes owned by Story 7.14: **interviewer cancellation** and **account deletion of the interviewer** (only interviewer account deletion refunds one credit; **scheduler account deletion does not** and is treated as a no-refund scheduler cancellation). Invalidate the account query after a cancellation initiated in the current client; for externally initiated cancellations, rely on the existing interview/account refetch-on-mount or focus behavior so the next dashboard/detail refresh shows the persisted balance from `GET /api/account` rather than inventing a client-side credit adjustment.

## Implementation Notes
- **Prerequisites**: Story 7.11 (shared contracts + policy metadata + durable claim-idempotency store), Story 7.15 (discovery + atomic claim route), Story 7.14 (premium booking cancellation/refund outcomes), and the Verified Interviewer Availability UI in Story 7.13 (the interviewer-facing publishing surface this scheduler consumes). Also Milestone 6 account/credit frontend contracts (`GET /api/account`, billing flow) and the Milestone 2 interview list/dashboard contract.
- The scheduler pays exactly one credit; the free-Standard quota never applies. This is a hard product rule reflected in the UI copy and not overridable.
- This ticket is the scheduler booking surface only; the verified-interviewer availability/slot-management surface is Story 7.13 (publish/manage UI) backed by Story 7.12 (availability API).
- `POST /api/interviews` remains AI-only; the claim route (Story 7.15) is the booking path. Standard matcher and join-time provisioning are unchanged.
- The v2 draft contract is a discriminated union. The v1→v2 migration is **lossless preservation of the valid normalized/restorable v1 state** for AI/P2P (matching the exact v2 envelopes above — no byte-for-byte guarantee beyond those restorable shapes) and additive-only for the new `verified_interviewer` branch. Do not repurpose a v1 P2P draft as a Premium claim.
- The Premium UI is system-design-only: this UI requests/renders only `system_design` inventory. The shared/backend contracts preserve the full enum values for future compatibility; this UI simply never presents the other values.

## End Goal
Schedulers can choose the Verified Interviewer branch inside `/interviews/new`, browse a safe, public first-to-claim marketplace of `system_design` verified-interviewer slots, claim an available slot by paying exactly one credit with idempotent retries that survive reload/reopen via the durable `{ slotId, idempotencyKey, startedAt }` claim, and see the resulting booking in their interviews plus the correct credit outcome for scheduler-initiated vs interviewer-cancellation/account-deletion outcomes — all built on the Story 7.11/7.14/7.15 contracts without leaking private interviewer data and without regressing the existing AI/P2P scheduling draft.
