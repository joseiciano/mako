# Story 7.2: Employment History API

**Milestone**: Milestone 7: Interviewer Verification & Premium Matching
**Description**: Complete authenticated employment-history CRUD using the Story 7.1 contracts so users can create, correct, and soft-delete the canonical records later selected by interviewer applications.
**Status**: Todo

## What Needs to Be Done

### 1. Repository Layer
- [ ] Extend the existing account/company repository using raw SQL through Hyperdrive and the controller-service-repository pattern in `docs/coding/backend-instructions.md`.
- [ ] List only the authenticated user's active rows (`deleted_at IS NULL`) with deterministic `ORDER BY joined DESC, created_at DESC, id ASC`.
- [ ] Create records with a UUID and `created_at`/`updated_at` generated by trusted backend application code (never client input); persist canonical date-only `start`/`end` at UTC midnight in `joined`/`ended_at`, plus `role`.
- [ ] Implement owner-scoped update and soft-delete queries using both `id` and `user_id`. Update sets `updated_at`; delete sets `deleted_at` and `updated_at` together and does not physically remove the row.
- [ ] Return zero-row outcomes so the service maps unknown, deleted, and non-owned records to the same `404` without revealing another user's data.

### 2. Service and Validation
- [ ] Move company request/response validation from duplicated backend/frontend declarations to the Story 7.1 schemas exported by `@mako/shared`.
- [ ] Require an authenticated active account for every operation. Define active-account error semantics consistently across all employment-history routes: unauthenticated requests return `401`; authenticated requests from an inactive or soft-deleted account return `403` (fail closed, no partial data, no distinction between invalid/unknown statuses that would leak account state).
- [ ] Normalize and validate create/update input before repository calls, including company lowercase normalization, non-blank role, date-only values, and `end >= start`.
- [ ] Map legacy rows with `role = null` to `isComplete: false`; canonical creates and successful updates return `isComplete: true`.
- [ ] Ensure updating or deleting an employment record never changes `"user".companies` and never mutates an existing application snapshot.

### 3. Controller and Route Contracts
- [ ] Keep `GET /api/companies` and `POST /api/companies`, and add `PATCH /api/companies/:id` and `DELETE /api/companies/:id` in the existing account controller registration.
- [ ] `GET /api/companies` returns `{ companies: EmploymentRecordCompatibilityResponse[] }`.
- [ ] `POST /api/companies` accepts canonical `{ company, role, start, end }` and returns `{ company: EmploymentRecordCompatibilityResponse }` with `201`.
- [ ] `PATCH /api/companies/:id` accepts canonical `{ company, role, start, end }` and returns `{ company: EmploymentRecordCompatibilityResponse }` with `200`; the route performs a complete replacement of editable employment fields rather than ambiguous partial updates.
- [ ] `DELETE /api/companies/:id` returns `{ success: true }` with `200` after soft deletion.
- [ ] Active-account outcomes: inactive/deleted accounts return `403` consistently; invalid JSON, UUIDs, or fields return `400`; unauthenticated requests return `401`; unknown/deleted/non-owned records return `404`.
- [ ] Set `Cache-Control: private, no-store` on every employment-history response.

### 4. Coordinated Compatibility Rollout
- [ ] Accept the legacy `POST /api/companies` body `{ company, joined }` for the entire Milestone 7 (not just a transition window); store it with `role = NULL`, return `isComplete: false`, and emit a structured deprecation log without recording company or role values.
- [ ] Enforce exact canonical and mixed-payload behavior: a body containing only canonical fields `{ company, role, start, end }` is canonical; a body containing only legacy fields `{ company, joined }` is legacy; any mixed payload that combines legacy `joined` with canonical `start`/`end`/`role` returns `400` and persists nothing. Only `joined` may be absent in canonical form, and only `start`/`end`/`role` may be absent in legacy form.
- [ ] Return the separately named `EmploymentRecordCompatibilityResponse` shape (defined by Story 7.1) from `GET`/`POST`/`PATCH` during Milestone 7, which includes the canonical record fields plus a deprecated `joined` ISO-8601 alias. The `joined` alias is **required (non-null) on every record returned throughout Milestone 7 — including canonical records** — and is derived from the persisted `joined` column (which stores `start` at UTC midnight per the repository persistence rule), so the alias is always present even when a canonical record did not originate from the legacy shape. Treat `start` as canonical; document the alias as temporary and do not use it in new frontend code.
- [ ] Record a **breaking-change note** in the API documentation that the `joined` alias is required on every `EmploymentRecordCompatibilityResponse` only for the duration of Milestone 7 and that both legacy `{ company, joined }` acceptance and the deprecated `joined` alias require a separate, explicitly approved breaking-change ticket before removal; they are not removed inline with another story.

### 5. Tests and Documentation
- [ ] Add repository tests for deterministic listing, canonical create, legacy create, update, soft delete, ownership scoping, timestamps, and zero-row handling.
- [ ] Add service/controller tests for all success responses and `400`/`401`/`403`/`404` outcomes, including invalid dates, end-before-start, malformed JSON, invalid IDs, mixed legacy+canonical payload rejection, and attempts to mutate another user's record.
- [ ] Test that update/delete leaves account-level interviewer eligibility unchanged and cannot alter a stored application snapshot.
- [ ] Update the Companies section of `docs/system/system-design/api-routes.md` with exact canonical and temporary compatibility contracts.

## Implementation Notes
- **Prerequisite**: Story 7.1 migration and shared contracts.
- No external verification service is called by these routes.
- Soft-deleted and incomplete records cannot be selected by the application integration in Story 7.5, but historical application snapshots remain valid.
- Do not add pagination for this bounded profile collection in the MVP.

## End Goal
Authenticated users can list, create, replace, and soft-delete their own employment records through typed, owner-scoped routes. Legacy records remain recoverable and editable, authorization fails closed, and profile edits cannot silently change past verification evidence or verified-interviewer eligibility.
