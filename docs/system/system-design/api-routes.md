# API Routes

> **Note**: All routes defined below (and any future routes) must be backed by shared, validated schemas in `@mako/shared`, documented exactly here with request/response shapes and error states, and locked down by contract tests. Generated OpenAPI/Swagger tooling is deferred to a separate repository-wide initiative; individual feature tickets must not introduce partial annotation conventions.

### Authentication (Better Auth 1.5.6)

- **`POST /api/auth/sign-up/email`**
  - **Description**: Registers an email/password account and requests email verification. Social sign-up uses Better Auth's provider-specific endpoints, not this route.
  - **Request Body**: `{ email: string, password: string, name: string, callbackURL?: string, rememberMe?: boolean }`. The application sends an absolute trusted frontend callback URL ending in `/login?verified=true`.
  - **Success Response (`200`)**: `{ user: User, token: null }`. For a new account, `user.emailVerified` is `false`; Better Auth creates no session and sets no usable authentication token.
  - **Enumeration Safety**: When the email already belongs to an account, Better Auth returns the same success shape with a synthetic unverified user and `token: null`. A successful response therefore does not reveal whether an account was created or already existed. The frontend treats both outcomes identically and navigates to `/verify-email` without displaying the submitted address.
  - **Delivery Semantics**: For a newly created account, verification delivery is scheduled asynchronously on the originating Worker request. The HTTP success means the unverified account was created and background work was registered; it does not prove provider acceptance or mailbox delivery. A later provider rejection does not roll back the account, mark it verified, or create a session. The account remains unusable until verified and can request a fresh link by attempting a correct-password sign-in.

- **`POST /api/auth/sign-in/email`**
  - **Description**: Authenticates an email/password account and establishes a secure session cookie only after the email has been verified.
  - **Request Body**: `{ email: string, password: string, callbackURL?: string, rememberMe?: boolean }`
  - **Success Response (`200`)**: `{ redirect: boolean, token: string, url?: string, user: User }`. `redirect` and `url` reflect an optional callback URL; the session cookie is established for a verified account.
  - **Unverified Response (`403`)**: Correct credentials for an unverified password account trigger a fresh asynchronous verification message and return a JSON body of the shape `{ message: string, code: "EMAIL_NOT_VERIFIED" }`. No session is created. The application branches on `code` only and never renders the provider `message` text. Wrong credentials return the enumeration-safe `401 { message, code: "INVALID_EMAIL_OR_PASSWORD" }` response and do not disclose account existence.
  - **Delivery Failure**: Provider rejection can occur after the route has returned `EMAIL_NOT_VERIFIED`. It is observed through fixed, PII-safe telemetry but does not change authentication state or roll back the account.

- **`GET /api/auth/verify-email`**
  - **Description**: Verifies the signed email-verification token generated by Better Auth.
  - **Query Params**: `token: string` and optional `callbackURL: string`. Application-generated links use the absolute trusted frontend callback URL `https://<frontend-origin>/login?verified=true`; Better Auth appends the outcome as a query parameter.
  - **Valid Token with Callback (`302`)**: Sets `user.emailVerified = true` and responds with an HTTP `302` redirect to the callback URL — for the application callback: `https://<frontend-origin>/login?verified=true`. Verification does not create a session; the user must sign in normally afterward.
  - **Expired Token with Callback (`302`)**: Responds `302` to `<callbackURL>?error=TOKEN_EXPIRED`, producing `https://<frontend-origin>/login?verified=true&error=TOKEN_EXPIRED` for the application callback.
  - **Malformed or Invalid Token with Callback (`302`)**: Responds `302` to `<callbackURL>?error=INVALID_TOKEN`, producing `https://<frontend-origin>/login?verified=true&error=INVALID_TOKEN` for the application callback. A valid token whose account no longer exists redirects with `error=USER_NOT_FOUND`; the frontend intentionally renders only the allowlisted `TOKEN_EXPIRED` and `INVALID_TOKEN` link errors and never displays arbitrary query text. When the callback URL already contains a query string, Better Auth appends `&error=<code>` instead of `?error=<code>`.
  - **No Callback**: Without `callbackURL`, Better Auth does not redirect. Success returns `200 { status: true, user: null }`; expired and invalid tokens return `401 { message, code: "TOKEN_EXPIRED" | "INVALID_TOKEN" }` (and `401 { message, code: "USER_NOT_FOUND" }` for an unknown account). The application always supplies the callback URL, so this branch is reached only by direct API calls.
  - **Token Semantics**: Tokens are stateless HS256 JWTs signed by Better Auth and expire after one hour (`3600` seconds). They are not stored in the generic `verification` table, cannot be individually revoked, and are not strictly single-use. Replaying a still-valid token after the account is verified performs no new state transition and follows the callback again. Deleting the account makes its outstanding links unusable.
  - **Banner Precedence**: If the callback contains both `verified=true` and an allowlisted `error`, the frontend displays the error state and suppresses the verified-success state.

- **`POST /api/auth/sign-out`**
  - **Description**: Invalidates the current session and clears authentication cookies.
  - **Request Body**: None
  - **Response Body**: `{ success: boolean }`

- **`GET /api/auth/get-session`**
  - **Description**: Validates the current session and returns the authenticated user's data.
  - **Request Body**: None
  - **Response Body**: `{ user: User, session: Session } | null`

### Account Management
- **`GET /api/account`**
  - **Description**: Retrieves the current authenticated user's profile, credit balance, and remaining free interview quotas.
  - **Request Body**: None
  - **Response Body**:
    ```json
    {
      "id": "uuid",
      "email": "user@example.com",
      "displayName": "Jane Candidate",
      "credits": 8,
      "freeStandardInterviews": 1,
      "freeAiInterviews": 1,
      "isVerifiedInterviewer": false,
      "createdAt": "2026-01-01T00:00:00.000Z"
    }
    ```
  - **Field Mapping**: API response uses camelCase JSON fields mapped from DB columns `name`, `credits`, `free_standard_interviews`, `free_ai_interviews`, `created_at`. `isVerifiedInterviewer` is sourced from the authenticated user's `"user".companies` flag (the Story 7.8 eligibility flag); it supports the verified-only frontend navigation gate but is **never** an authorization source for backend premium routes.
  - **Query Params**: None

- **`PATCH /api/account`**
  - **Description**: Updates user profile information (display name).
  - **Request Body**: `{ displayName: string }`
  - **Response Body**: Same shape as `GET /api/account`.
  - **Query Params**: None

- **`DELETE /api/account`**
  - **Description**: Soft-deletes the user's account and cancels all active sessions.
  - **Request Body**: None
  - **Response Body**: `{ success: boolean }`
  - **Query Params**: None

### Interviewer Onboarding
- **`POST /api/interviewer/apply`**
  - **Description**: Submits an application to become a verified interviewer.
  - **Request Body**: `{ email: string, employmentRecordIds: UUID[] }` with 1–10 unique IDs.
  - **Response Body**: `{ application: InterviewerApplication }`
  - **Query Params**: None
  - **Status Codes**: `201` success; `400` malformed JSON, invalid fields, or invalid employment selection; `401` unauthenticated; `403` authenticated inactive/deleted account; `409` pending/approved eligibility or concurrent active-state conflict.
  - **Behavior Rules**:
    - `email` is a validated, user-supplied contact email and may differ from the authenticated account email. It is stored as immutable submission data.
    - Every selected record must be active, complete, and owned by the authenticated applicant.
    - The server reads the records and atomically persists an immutable `employmentHistory` snapshot shaped as `{ sourceCompanyId, company, role, start, end }[]`; clients do not submit trusted snapshot fields.
    - `start`/`end` are date-only strings and `end` is null for a current role.
    - Profile edits after submission do not rewrite the application snapshot or automatically revoke eligibility.

- **`GET /api/interviewer/status`**
  - **Description**: Retrieves the status of the current user's interviewer application.
  - **Request Body**: None
  - **Response Body**: `{ application: InterviewerApplication | null }`
  - **Query Params**: None
  - **Status Codes**: `200` success; `401` unauthenticated; `403` authenticated inactive/deleted account.
  - **Behavior Rules**: Returns the current user's latest application using deterministic `created_at DESC, id DESC` ordering. This returns the latest rejected row when no newer reapplication exists and the newer pending/decided row after reapplication.

`InterviewerApplication` is exactly `{ applicationId: UUID, email: string, employmentHistory: { sourceCompanyId: UUID | null, company: string, role: string, start: YYYY-MM-DD, end: YYYY-MM-DD | null }[], status: 'pending' | 'approved' | 'rejected', createdAt: ISO-8601, updatedAt: ISO-8601 }`. Applicant routes do not expose reviewer identity. New submissions always populate a non-null `sourceCompanyId`; null remains read-compatible only for controlled pre-contract data. Both routes set `Cache-Control: private, no-store`.

### Payments & Credits
- **`GET /api/payments/packages`**
  - **Description**: Returns the list of available credit packages (server-side source of truth for price-to-credit mapping). Authenticated route.
  - **Request Body**: None
  - **Response Body**:
    ```json
    {
      "packages": [
        {
          "package_id": "credits_5",
          "display_name": "5 Credits",
          "amount_cents": 2500,
          "credits_granted": 5
        },
        {
          "package_id": "credits_10",
          "display_name": "10 Credits",
          "amount_cents": 4500,
          "credits_granted": 10
        },
        {
          "package_id": "credits_20",
          "display_name": "20 Credits",
          "amount_cents": 8000,
          "credits_granted": 20
        }
      ]
    }
    ```
  - **Field Mapping**: `amount_cents` is the Stripe Payment Intent amount in USD cents. `credits_granted` is the number of interview credits granted on successful payment. The frontend must not derive credit amounts independently.
  - **Query Params**: None

- **`POST /api/payments/create-intent`**
  - **Description**: Generates a Stripe Payment Intent for purchasing interview credits.
  - **Request Body**: `{ package_id: string }`
  - **Response Body**: `{ client_secret: string }`
  - **Behavior Rules**:
    - Route is authenticated; unauthenticated requests receive 401.
    - `package_id` is validated against the server-side package configuration; unknown packages are rejected with 400.
    - Creates a Stripe Payment Intent with `amount` resolved from the package config, `currency: "usd"`, and `metadata` containing `package_id` and `user_id`.
    - Does not store the Payment Intent at creation time; the webhook handler creates the authoritative transaction record.
    - Credit balance does not change until the webhook processes `payment_intent.succeeded`.
  - **Query Params**: None

- **`POST /api/payments/webhook`**
  - **Description**: Stripe webhook handler for fulfilling credit purchases. (Internal only)
  - **Request Body**: `Stripe.Event`
  - **Response Body**: `200 OK`
  - **Behavior Rules**:
    - Verifies the Stripe webhook signature using `STRIPE_WEBHOOK_SECRET` before processing; invalid signatures return 400.
    - Handles `payment_intent.succeeded`: resolves `credits_granted` from package config via `metadata.package_id` and grants credits via the credit service. Idempotent via the unique constraint on `Credit_Transactions.stripe_payment_intent_id`.
    - Handles `payment_intent.payment_failed`: logs the failure with payment intent id and user context; does not affect balances.
    - Returns `200 OK` for all recognized event types to acknowledge receipt.
    - Does not send email or push notifications (notification scope belongs to the notification service).
  - **Query Params**: None

- **`GET /api/account/transactions`**
  - **Description**: Returns paginated credit transaction history for the authenticated user, sorted newest first (`created_at DESC`). Route is authenticated; unauthenticated requests receive 401. All rows are scoped to the authenticated `userId`.
  - **Request Body**: None
  - **Response Body**:
    ```json
    {
      "transactions": [
        {
          "id": "uuid",
          "amount": 2500,
          "credits_granted": 5,
          "status": "succeeded",
          "created_at": "2026-06-24T12:00:00.000Z"
        }
      ],
      "total": 1
    }
    ```
  - **Field Mapping**: Response uses snake_case and exposes only user-safe ledger fields (`id`, `amount`, `credits_granted`, `status`, `created_at`). Internal fields (`user_id`, `stripe_payment_intent_id`, webhook metadata) are never exposed.
  - **Query Params**: `limit?: number` (default 20, max 100), `offset?: number` (default 0). Invalid pagination values receive 400.

### Interviews
- **`POST /api/interviews`**
  - **Description**: Schedules or initializes a new interview session.
  - **Current Milestone 2 Contract**:
    - Direct creation is supported for **AI-led** sessions.
    - Direct **peer-to-peer** creation is not supported; peer-to-peer Standard sessions are created by the Availability + Greedy Matcher flow.
    - Client payload does **not** set `tier`; effective interview tier/policy is resolved server-side from account state (for example: free vs subscribed) and quota/credit rules.
    - `interviewer_id` is out of scope for this route contract and must not be provided.
    - Default policy resolution examples:
      - `free_ai_interviews > 0` → request is accepted and consumes free AI quota with resolved tier label `standard` by default policy config.
      - `free_ai_interviews = 0` and `credits > 0` → request is accepted and consumes one credit with resolved tier label `premium` by default policy config.
      - `free_ai_interviews = 0` and `credits = 0` → request is rejected with an explicit business-rule error.
    - Rejected combinations:
      - `mode: 'peer_to_peer'`
      - any request containing `interviewer_id`
      - any request containing client-selected `tier`
    - **Cross-Channel Overlap Rejection**: Direct creation rejects with `InterviewPolicyConflictError` (409) if the requesting user already has a scheduled or ongoing interview whose window overlaps the requested time. This prevents double-booking across booking channels (AI-direct, standard match, and verified-interviewer premium claims). The greedy matcher also skips `scheduling_conflict` availability slots that overlap existing interviews.
  - **Workflow**:
    - **Scheduled Sessions**: After successful validation and policy reservation, persists the interview record. Confirmation/reminder orchestration is not part of the current create-route runtime behavior.
    - **Immediate AI Sessions**: If `mode: 'ai_led'` and `scheduled_at` is set to `'now'`, the interview is created with immediate timing semantics, but realtime/whiteboard provisioning remains join-time via `POST /api/interviews/:id/provision` (not in create-route transaction scope).
  - **Request Body**: `{ type: 'system_design' | 'coding' | 'behavioral', mode: 'ai_led', scheduled_at: ISO-8601 timestamp string | 'now' }`
  - **Response Body**: `{ interview: Interview }`
  - **Query Params**: None

- **`GET /api/interviews`**
  - **Description**: Lists interviews for the current user as a narrow summary.
  - **Request Body**: None
  - **Response Body**:
    ```json
    {
      "interviews": [
        {
          "id": "uuid",
          "scheduler_id": "uuid",
          "scheduler_alias": "Candidate-Blue",
          "interviewer_id": null,
          "interviewer_alias": "Interviewer-Red",
          "type": "system_design",
          "mode": "peer_to_peer",
          "tier": "standard",
          "booking_channel": "standard_match",
          "status": "scheduled",
          "scheduled_at": "2026-01-01T12:00:00.000Z",
          "created_at": "2026-01-01T00:00:00.000Z",
          "updated_at": "2026-01-01T00:00:00.000Z"
        }
      ]
    }
    ```
  - **Field Mapping**: API response uses snake_case and maps directly to DB columns.
  - **Summary-only Contract**: The list response intentionally excludes detail-only fields (`realtime_session_id`, `excalidraw_room_id`, `excalidraw_key`, `recording_url`, `screenshot_urls`, `feedback`). Use `GET /api/interviews/:id` for the full detail payload.
  - **Role Semantics**:
    - For matcher-created peer-to-peer interviews, `scheduler_id` / `interviewer_id` are assigned deterministically from matched request order `(created_at ASC, id ASC)`.
    - For direct route-created sessions in Milestone 2, `scheduler_id` is the authenticated creator.
  - **Query Params**: `status?: 'scheduled' | 'ongoing' | 'completed' | 'cancelled'`, `limit?: number`, `offset?: number`

- **`POST /api/interviews/:id/cancel`**
  - **Description**: Cancels a scheduled interview.
  - **Request Body**: None
  - **Response Body**: `{ success: boolean }`
  - **Query Params**: None

- **`POST /api/interviews/:id/provision`**
  - **Description**: Provisions (or returns existing) Cloudflare Realtime + Excalidraw collaboration credentials for interview join. This is the join-time credential route.
  - **Request Body**: None
  - **Response Body**:
    ```json
    {
      "mode": "peer_to_peer",
      "realtime": {
        "realtime_session_id": "rt_session_123",
        "token": "rt_token_abc"
      },
      "excalidraw": {
        "excalidraw_room_id": "wb_room_123",
        "excalidraw_key": "wb_key_abc"
      }
    }
    ```
  - **Canonical Provision Contract**: Response field names intentionally match persisted interview columns where applicable. `realtime.realtime_session_id` maps to `interviews.realtime_session_id`; `excalidraw.excalidraw_room_id` maps to `interviews.excalidraw_room_id`; `excalidraw.excalidraw_key` maps to `interviews.excalidraw_key`. `realtime.token` is an ephemeral join token and is not stored on the interview row.
  - **Mode Contract**: `mode` is either `peer_to_peer` or `ai_led` and determines whether credentials represent a shared two-participant collaboration room or a single-user interview-scoped room.
  - **Behavior Rules**:
    - Route is participant-only (interview participants can provision/join; non-participants are rejected).
    - Provisioning is join-time runtime behavior and does not introduce a separate persisted interview `status`.
    - Retries/reconnects for the same active interview are idempotent and must reuse existing persisted values when present.
    - `peer_to_peer`: both participants receive credentials for the same shared room/key pair.
    - `ai_led`: return a single-user room/key pair scoped to the interview.
    - Credentials returned here are not exposed through `GET /api/interviews`; use this route at join-time.
    - Voice does not bypass or own provisioning; join-time credential ownership remains exclusively with this route.
  - **Query Params**: None
  - **Telemetry**: Structured logs are emitted at provision lifecycle points: `interview.provision_start` (with `interview_id`, `participant_user_id`), `interview.provision_success` (with `interview_id`, `outcome`), and `interview.provision_failure` (with `interview_id`, `error_type`). Logs must not leak sensitive collaboration credentials (`excalidraw_key`, realtime tokens).

- **`POST /api/interviews/:id/start`**
  - **Description**: Starts an interview session for a participant and transitions lifecycle state from `scheduled` to `ongoing` when valid.
  - **Request Body**: None
  - **Response Body**:
    ```json
    {
      "success": true,
      "interview": {
        "id": "uuid",
        "scheduler_id": "uuid",
        "scheduler_alias": "Candidate-Blue",
        "interviewer_id": "uuid",
        "interviewer_alias": "Interviewer-Red",
        "type": "system_design",
        "mode": "peer_to_peer",
        "tier": "standard",
        "booking_channel": "standard_match",
        "status": "ongoing",
        "scheduled_at": "2026-04-10T10:30:00.000Z",
        "recording_url": null,
        "screenshot_urls": null,
        "feedback": null,
        "recording_status": "not_started",
        "transcript": null,
        "feedback_status": "not_started",
        "feedback_unavailable_reason": null,
        "feedback_error_code": null,
        "feedback_prompt_version": null,
        "feedback_generated_at": null,
        "started_at": "2026-04-10T10:30:00.000Z",
        "expires_at": "2026-04-10T11:30:00.000Z",
        "warning_at": "2026-04-10T11:25:00.000Z",
        "created_at": "2026-04-01T10:00:00.000Z",
        "updated_at": "2026-04-10T10:30:00.000Z"
      }
    }
    ```
  - **Behavior Rules**:
    - Route is participant-only; unauthenticated requests receive 401; missing or non-participant requests receive 404.
    - Valid transition: `scheduled -> ongoing`.
    - Idempotent retry: repeated `start` on already `ongoing` interview returns `{ success: true, interview }` without conflicting state mutation.
    - Invalid transitions (`cancelled -> start`, `completed -> start`) are rejected with 409 without state mutation.
    - Successful `start` is the persisted lifecycle boundary that triggers active workflow timer orchestration (60-minute session, 5-minute warning).
    - Start is atomic guarded (`AND status = 'scheduled'`) and idempotent on retry (`already_ongoing`). Concurrent starts converge to one deterministic `ongoing` state.
    - Response uses credential-safe `InterviewDetail` schema (excludes `realtime_session_id`, `excalidraw_room_id`, `excalidraw_key`).
    - Voice does not bypass or own the start boundary; lifecycle transition ownership remains exclusively with this route.
  - **Telemetry**: Structured logs emit `start_requested` and `start_succeeded` with safe context (`interview_id`, `participant_user_id`, `action`, `outcome`, `status`, timer fields). No secrets logged.
  - **Query Params**: None

- **`POST /api/interviews/:id/ai-chat`**
  - **Description**: Submits a user chat turn for AI-led interviews and returns guidance/review grounded in chat context + Excalidraw canvas snapshot.
  - **Request Body**:
    ```json
    {
      "message": "What should I add next?",
      "canvas_snapshot": {
        "type": "excalidraw_scene",
        "scene": {}
      },
      "guidance_mode": "review",
      "chat_history": [
        { "role": "user", "content": "previous question" },
        { "role": "assistant", "content": "previous answer" }
      ]
    }
    ```
  - **Response Body**:
    ```json
    {
      "reply": "You're missing a cache invalidation strategy between services A and B.",
      "guidance_mode": "review",
      "prompt_version": "system-design-review-v1"
    }
    ```
  - **Error Responses**:
    - `400 Bad Request` — invalid request body or route parameter (schema validation failure).
    - `401 Unauthorized` — unauthenticated request.
    - `404 Not Found` — interview not found or participant not on the interview.
    - `422 Unprocessable Entity` — valid request but interview mode is `peer_to_peer` (AI chat only for `ai_led`).
    - `502 Bad Gateway` — upstream AI provider returned an error (non-OK HTTP status, malformed JSON, or empty reply). The response body contains `{ "error": "<detail>" }`.
    - `503 Service Unavailable` — AI chat is not configured or upstream provider is unreachable (missing credentials, network failure, or timeout). The response body contains `{ "error": "<detail>" }`.
   - **Behavior Rules**:
     - Route is only valid for `mode = 'ai_led'` interviews.
     - Route is participant-only.
     - Canvas input must be Excalidraw JSON (`type: "excalidraw_scene"`). The schema enforces the Excalidraw literal type; Mermaid is optional downstream output, not required request input.
      - `chat_history` is optional; when provided it is bounded to 8 messages and inserted between the system prompt and user message. Each history `content` is bounded to 750 characters and the current `message` is bounded to 2000 characters.
      - `prompt_version` identifies the active backend-owned prompt definition. As of Story 4.6 the version is `system-design-review-v1` (system-design interviewer guidance). The version is defined in `packages/shared-backend/src/interviews/ai-chat-prompt.ts` and is derived from the retrieved interview's `type`.
      - Prompt behavior: for `system_design` interviews the system prompt instructs runtime interviewer guidance (not grading/report generation), a review-oriented style (clarifying questions, gap detection, tradeoff probing, next-step hints), grounding only on the supplied snapshot/context, explicit acknowledgement of uncertain or missing context, and a prohibition on controlling session lifecycle/timers or claiming canvas edits. Guidance is succinct and candidate-facing.
      - Forward compatibility: `coding` and `behavioral` interview types receive a safe unsupported-type fallback prompt that states specialized guidance is not available yet and does not pretend a system-design prompt applies.
      - Clients should send snapshots on explicit review actions and/or debounced intervals (not per-stroke).
      - AI requests bypass cache (`cf-aig-skip-cache: true`) because the canvas snapshot context is mutable.
  - **Voice Wrapper Contract**:
    - Voice is an ephemeral runtime wrapper only, scoped to `mode = 'ai_led'` sessions on `/interviews/:id/session`.
    - Speech-to-text input submits the same `message` field and the full existing request contract described above to this route; text-to-speech playback renders the same `reply` field returned in the response.

### Premium Scheduling (Milestone 7)

First-to-claim premium marketplace for verified-interviewer slots. Shared premium contracts: `BookingChannel = 'ai_direct' | 'standard_match' | 'verified_interviewer'`; `PremiumSlotStatus = 'available' | 'claimed' | 'cancelled'`; `PremiumInterviewerSlot = { id: UUID, interviewerId: UUID, interviewType: 'system_design' | 'coding' | 'behavioral', startTime: ISO-8601, endTime: ISO-8601, status: PremiumSlotStatus, createdAt: ISO-8601, updatedAt: ISO-8601 }`; `PremiumPolicyMetadata = { leadTimeMinutes: positive integer, horizonDays: positive integer, priceCredits: 1 }` — `priceCredits` is the literal `1` and is not configurable in this milestone.

  - **Response Body**: Exactly `{ success: true }`.
  - **Query Params**: None.
  - **Status Codes**: `200`; `401` unauthenticated; `403` authenticated inactive/deleted (`{ error: 'ACCOUNT_INACTIVE' }`) or non-eligible interviewer; `404` unknown/non-owner slot without leaking existence; `409` slot already claimed.

- **`POST /api/premium/marketplace/slots/:id/claim`**
  - **Description**: Atomically claims an available premium slot, deducting exactly one scheduler credit and creating the interview in one transaction. Owned by Story 7.15.
  - **Request Headers**: `Idempotency-Key: <UUID>` (required).
  - **Request Body**: None.
  - **Response Body**: Exactly `{ interview: InterviewDetail }` — the credential-safe interview detail schema excluding provision-only `realtime_session_id`, `excalidraw_room_id`, and `excalidraw_key` fields, matching the existing `GET /api/interviews/:id` / start / end detail contract.

### Provider Webhooks
- **`POST /api/webhooks/realtimekit`**
  - **Description**: Signed RealtimeKit recording status webhook handler. Provider webhook route that does not use browser-session authentication.
  - **Request Body**: Provider webhook event payload (`recording.statusUpdate`).
  - **Response Body**: `200 OK`
  - **Behavior Rules**:
    - Reads raw request bytes and verifies Base64 RSA-SHA256 `rtk-signature` using a cached, refreshable public key fetched from `REALTIMEKIT_WEBHOOK_PUBLIC_KEY_URL` (`https://api.realtime.cloudflare.com/.well-known/webhooks.json`) before parsing JSON. Requests with invalid signatures are rejected; no state is mutated. Verification re-fetches the key on first failure and returns `503` when key infrastructure is unavailable.
    - Idempotent via `rtk-uuid` as `provider_event_id` primary key on `realtimekit_webhook_events`; duplicate delivery is safely acknowledged.
    - Validates the supported `recording.statusUpdate` payload and acknowledges unsupported, validly signed event types without side effects.
    - Maps RealtimeKit provider states to internal recording transitions without regression: `INVOKED`/`RECORDING` → `accepted`, `UPLOADING` → `finalizing`, `UPLOADED` → `processed`, `ERRORED` → `failed`. Out-of-order and repeated states are idempotent no-ops with diagnostics preserved.
    - Resolves the specific `interview_recordings` row and owning interview by persisted provider recording ID rather than trusting interview/user identifiers in webhook payloads.
    - Persists the accepted webhook event/checkpoint and provider state in one short transaction then returns `2xx` (fast acknowledgement); does not download media in the webhook request. Only safe error codes are persisted for terminal `ERRORED` failures.
    - On accepted `UPLOADED`, triggers the dedicated `RecordingFinalizationWorkflow` via `RECORDING_FINALIZATION_WORKFLOW.createBatch` with deterministic instance ID `recording-finalization-v1-{provider-recording-id}` and strict payload `{ recording_id: UUID, schema_version: 1 }` (also referenced as `recording_finalization` workflow). The `createBatch` call occurs only after `COMMIT`; trigger failure still returns `2xx` so the scheduled sweep can recover. Duplicate webhook delivery reuses the deterministic instance without parallel copies.
    - The `RecordingFinalizationWorkflow` fetches fresh recording/track status and short-lived download URLs from RealtimeKit by provider recording ID inside the workflow; signed download URLs are never persisted to SQL, logs, workflow return values, or step state. Downloads are streamed as `ReadableStream` directly to private `RECORDINGS_BUCKET` under canonical keys `interviews/{interviewId}/recording/{artifactUuid}` without materializing the full buffer, validating HTTPS origin, response status, content type, participant/role mapping, and bounded metadata.
    - Handles participant roles: a single TRACK provider recording ID can return multiple participant files — the workflow iterates every `download_url[].download_urls` entry, parses the encoded `user_id` from the filename, validates it against canonical interview scheduler/interviewer IDs, maps scheduler→`candidate` and peer interviewer→`interviewer`, and persists one `transcription_audio` artifact per file; composite is persisted as a single `playback_recording` artifact only. Never uses mixed composite audio for scoring. Canonical R2 keys remain `interviews/{interviewId}/recording/{artifactUuid}`; provider asset uniqueness is enforced durably.
    - Bounded sweep recovery: the scheduled `*/5 * * * *` trigger in `notification-orchestrator` owns sweep/restart and is bounded over `UPLOADED` pending/failed rows by recording ID, reuses the same deterministic workflow IDs, restarts terminal skipped instances, and re-invokes `RecordingFinalizationWorkflow` for retry-safe recovery; recording transfer is never delegated to `FEEDBACK_WORKFLOW` or `InterviewFeedbackWorkflow`.
    - Does not expose provider error bodies to clients.
  - **Query Params**: None
