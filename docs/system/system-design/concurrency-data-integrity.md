To ensure system reliability, especially regarding financial transactions and interview scheduling, the following strategies are implemented:

- **Credit Updates**: All balance updates are performed using atomic SQL operations (e.g., `UPDATE "user" SET credits = credits + ?`) within a database transaction. This prevents race conditions where multiple concurrent updates could lead to incorrect balances.
- **Tier Policy Resolution**: When the free-tier policy service must read account state (quotas + credits), decide which resource to consume, then write — a read-decide-write pattern not expressible as a single atomic UPDATE — it uses `SELECT ... FOR UPDATE` on the user row within the interview-creation transaction to prevent race conditions between concurrent interview creation attempts.
- **Idempotency**: Stripe webhook handlers utilize the `stripe_payment_intent_id` as an idempotency key. Before granting credits, the system checks the `Credit_Transactions` table to ensure the specific payment hasn't already been fulfilled.
- **Greedy Matcher (Concurrency)**: To prevent over-matching, the "Greedy Matcher" cron worker executes each match attempt inside a Postgres transaction and uses `SELECT ... FOR UPDATE` to lock candidate `Availability_Slots` and their parent `Availability_Requests`.
- **Greedy Matcher Conflict Handling**: Retryable transaction conflicts (`40001`, `40P01`) are retried with bounded attempts; exhausted conflicts are skipped with deterministic diagnostics so the cycle can continue safely.
- **Quota Enforcement**: Within the matching transaction, the system checks `current_matches < max_matches`. If a match is made, `current_matches` is incremented. If the limit is reached, all other slots for that request are immediately cancelled to prevent redundant matching.
- **Matcher Observability**: Every run emits lifecycle events (`matcher.run.started`, `matcher.run.completed`) with `run_id` and lightweight counters (`slotsScanned`, `pairsAttempted`, `matchesCreated`, `transactionConflicts`, `transactionRetries`).
- **Post-Commit Publish-Failure Observability**: If post-commit event emission fails after a match write commits, the run emits `matcher.run.post_commit_publish_failure` with `run_id`, `attempt_key`, `slot_ids`, `request_ids`, `interview_id`, and `error_message`.
- **Lifecycle Transition Atomicity**: `POST /api/interviews/:id/start` and `POST /api/interviews/:id/end` must use atomic SQL transition guards so concurrent participant actions cannot create conflicting interview states.
- **Lifecycle Idempotency**: Repeated `start` on `ongoing` and repeated `end` on `completed` must return success semantics without duplicating writes or downstream orchestration.
- **Workflow Convergence**: Manual `end` and workflow timeout completion must converge to one deterministic terminal `completed` write; duplicate completion side effects must be prevented.
- **Lifecycle Conflict Handling**: Retryable transaction conflicts (`40001`, `40P01`) on lifecycle writes should be retried with bounded attempts and deterministic diagnostics.
- **Lifecycle Observability**: Lifecycle actions and timer convergence should emit structured events with enough context to debug race conditions without leaking Realtime tokens or Excalidraw secrets.
- **Scheduling Locks (Future Scope)**: Manual peer-to-peer Premium "First-to-Claim" with Postgres advisory locks is planned for a future milestone (Milestone 7), and is not part of Milestone 2 behavior.
- **Interviewer Application Snapshot Atomicity**: Application submission validates the user's application eligibility and all selected active/complete `user_companies` rows, builds the normalized employment snapshot, and inserts the application in one transaction. One partial unique index covering `status IN ('pending', 'approved')` prevents every duplicate active-state combination, including approval/submission races; one conflicting writer succeeds and the other returns `409`.
- **Interviewer Application Lock Order**: Application submission acquires row locks in a deterministic order to prevent deadlocks when submissions run concurrently. The transaction first locks the applicant `"user"` row with `SELECT ... FOR UPDATE`, then locks the selected `user_companies` rows with `SELECT ... FOR UPDATE` ordered by `id` ascending (UUID order). Because every submission acquires locks in the same global order, concurrent submissions serialize instead of deadlocking. After locking, the transaction revalidates that the user is still active and that every selected row is still active, complete, and owned by the applicant; any missing, foreign, deleted, duplicate, incomplete, or concurrently-removed selection is rejected with `400`. The partial unique index on `user_interviewer_applications(user_id) WHERE status IN ('pending', 'approved')` prevents duplicate active applications at the database boundary.
- **Employment Snapshot Immutability**: Submitted `employment_history` JSON is never synchronized from mutable profile rows. Later profile updates or soft deletion cannot race with or rewrite stored review evidence and do not automatically revoke `"user".companies` eligibility.
