### Public & Auth
- **Landing Page (`/`)**: Product value proposition, feature highlights, and entry points.
- **Login / Sign Up (`/login`, `/register`)**: Authentication forms handled via Better Auth.

### Dashboard & Account
- **Dashboard (`/dashboard`)**: Central hub showing upcoming interviews and quick stats (credits + free Standard/AI balances).
    - **Data**: `GET /api/account`, `GET /api/interviews?status=scheduled`
- **Interviews History (`/interviews`)**: A comprehensive list of all past and upcoming sessions.
    - **Data**: `GET /api/interviews`
- **Billing & Credits (`/billing`)**: Balance summary from `GET /api/account`; credit package selection from `GET /api/payments/packages` with single-package selection, and `POST /api/payments/create-intent` to initiate a Stripe Payment Intent (returns a client secret). Checkout and payment confirmation are handled by an embedded Stripe Payment Element, with `stripe.confirmPayment` completing the payment (including 3DS redirect handling) and the backend webhook granting credits asynchronously.
    - **Data**: `GET /api/account`, `GET /api/payments/packages`, `POST /api/payments/create-intent`
    - **Scope Note**: Payment amounts are never derived client-side; the backend package config is authoritative. Selected package and create-intent state are owned by the billing smart component and persisted to `sessionStorage` (`mako.billing.purchase`) so the checkout can be restored after a Stripe 3DS redirect.
- **Settings & Profile (`/settings`)**: Manage profile, employment history, and interviewer verification.
    - **Data**: `GET /api/account`, `PATCH /api/account`, `GET /api/interviewer/status`, `GET /api/companies`, `POST /api/companies`, `PATCH /api/companies/:id`, `DELETE /api/companies/:id`
    - **Employment History**: Users create, edit, and delete employment records with canonical `company`, `role`, `start` (YYYY-MM-DD), and optional `end` (YYYY-MM-DD, omitted via the "Current role" checkbox) fields via `POST /api/companies`, `PATCH /api/companies/:id`, and `DELETE /api/companies/:id`. The list renders the company, role, and a `start — end` range (`start — Present` when `end` is `null`), formatted directly from the canonical date strings without timezone parsing.
    - **Incomplete Records**: Migrated records missing a `role` render with a "Needs details" state (`isComplete === false`) and an edit action. Incomplete records must be completed before they can be selected for an interviewer application.
    - **Verification Boundary**: Applications select complete employment record IDs, while the server stores an immutable snapshot. Profile edits do not alter submitted evidence or automatically revoke account-level interviewer eligibility. Deleting a record never alters previously submitted applications.
- **Interviewer Application (`/settings/interviewer-application`)**: Authenticated users (route lives under `_authenticated`, so unauthenticated access redirects to `/login`) apply to become verified interviewers by selecting employment records. Linked from Settings ("Become a verified interviewer") for non-verified users.
    - **Data**: `GET /api/interviewer/status` (queried first, key `['interviewer', 'status']`), `GET /api/companies` (separate profile key), `POST /api/interviewer/apply`
    - **Status-first Flow**: No application shows the selection form; `pending` and `approved` show the submitted snapshot and status with resubmission disabled; `rejected` shows the prior snapshot plus a reapplication form.
    - **Employment Selection**: Only `isComplete === true` records are selectable (checkbox semantics, 1-10 unique selections). Incomplete records render as unavailable with a "Needs details" label and a link to the profile employment editor; empty history links to settings. The request contains only the editable contact email (prefilled from the account) and `employmentRecordIds` in profile list order; the client never submits company/role/date fields.
    - **Immutable Snapshot**: After success the returned application is written to the status cache and its `employmentHistory` is rendered (`Present` for a null end date); later profile edits do not change it. No per-employment verified badges are shown; application status is the verification state.
    - **Errors & Accessibility**: Validation and submit errors keep selections and email, with a retry path; focus moves to the first actionable error. A `409` refetches status and converges on the canonical pending/approved state. Loading and submitting states keep selected checkboxes in the accessibility tree.
- **Admin Application Review (`/admin/reviews`)**: Master-detail page for admins, under `_authenticated` (unauthenticated access redirects to `/login`). A route `beforeLoad` guard redirects non-admins (canonical session `user.isAdmin !== true`) to `/dashboard`; this is UX only and the API's `requireAdmin` remains the authority.
    - **Data**: `GET /api/admin/applications` (query keys `['admin','applications','list',{status,limit,offset}]`), `GET /api/admin/applications/:id` (key `['admin','applications','detail',id]`), `PATCH /api/admin/applications/:id` with `{ decision }`
    - **Master-Detail**: Status filter (`pending` default, `approved`, `rejected`), offset pagination (limit 25), and a detail panel with the employment snapshot. Loading, empty, and error (with retry) states for both panels.
    - **Decisions**: Approve/reject require a confirmation step. Success updates the detail cache, invalidates all list variants, and clears the selection. `409` shows a conflict notice and refetches list and detail. Deleted applicants (`isAccountDeleted`) cannot be approved; reject stays enabled. No reason or note is collected.
    - **Session Loss**: A later `401` clears admin caches and routes to `/login`; a `403` routes to `/dashboard`. Neither is retried and no response is written to the cache.
    - **Navigation**: The "Admin" entry (`/admin/reviews`) is added to the sidebar and mobile nav by `getNavigationItems(isAdmin)` in `app-shell-smart.tsx` only when the session user `isAdmin`.
- **Interviewer Availability (`/settings/interviewer-availability`)**: Verified interviewers publish and manage premium system design interview slots.
    - **Data**: `GET /api/premium/interviewer/slots?interviewType=system_design`, `POST /api/premium/interviewer/slots`, `DELETE /api/premium/interviewer/slots/:id`
    - **Eligibility**: Linked from Settings only when `GET /api/account` returns `isVerifiedInterviewer: true`. Non-verified users are redirected away.
    - **Publish Flow**: Collects a `startTime` and submits `{ interviewType: 'system_design', startTime }`. Interview type is fixed to `system_design` — no coding/behavioral controls. Client-side min/max date bounds from the policy metadata (`leadTimeMinutes`, `horizonDays`).
    - **Inventory**: Renders published slots with server-owned status badges (`available`/`claimed`/`cancelled`), the `system_design` type label, and the 60-minute window. Cancel is only available for `available` slots; `claimed` slots are non-cancellable.
    - **Cancel Reconciliation**: A concurrent `409` (slot became claimed) invalidates the slots query and refetches server state rather than leaving stale local assumptions.
    - **Accessibility**: Publish validation and conflict errors move focus to the first actionable error alert so screen-reader users are notified. Disabled cancel buttons and status badges convey state via text and ARIA, not only color.
    - **Scope Note**: This UI is for verified interviewers managing the slots they offer; it is distinct from the scheduler-facing marketplace booking UI.

### Interview Lifecycle
- **Schedule Interview (`/interviews/new`)**: Configuration flow with three submission branches — AI direct, Standard P2P via availability, and Verified Interviewer (premium first-to-claim marketplace). The interview type is System Design.
    - **Data**: `POST /api/interviews` (**AI-led only**), `POST /api/availability` (**P2P matching path**), `GET /api/premium/marketplace?interviewType=system_design` and `POST /api/premium/marketplace/slots/:id/claim` (**Verified Interviewer branch**)
    - **Branches**: The flow is a tagged discriminated union with exactly three submission branches — `ai_direct`, `standard_p2p`, `verified_interviewer` — plus a `pre_branch` variant for the pre-submission UI state.
    - **Premium Browse/Claim**: The Verified Interviewer branch requests and renders **only `system_design`** marketplace inventory — no coding/behavioral filter or selector. Slots render safe public fields only: interviewer display name, optional image, verified badge, `system_design` type label, and the 60-minute window. No application/private employment/reviewer/contact/company-role fields. The claim sends a UUID `Idempotency-Key`; both the initial `201` and same-key replay `200` reconcile to the created booking. `409` literals are handled distinctly: `PREMIUM_SLOT_ALREADY_CLAIMED` and `PREMIUM_INTERVIEWER_INELIGIBLE` are terminal after marketplace refetch; `INSUFFICIENT_CREDITS` links to billing; `PREMIUM_SCHEDULING_CONFLICT` explains the conflict and allows same-slot retry; `IDEMPOTENCY_KEY_CONFLICT` stops automatic retries and requires a new logical claim/key (same-slot resubmit atomically replaces the durable key and resets `startedAt`).
    - **Price Note**: A claim costs **exactly one credit** (`policy.priceCredits: 1`); the free-Standard quota never applies. This is a hard product rule reflected in the UI copy and not overridable. Credit balance comes from `GET /api/account`.
    - **Policy Note**: Account tier/policy (for example free vs subscribed) is resolved server-side; scheduling UI does not submit a user-selected `tier` field.
    - **Create Matrix Note**: Direct create UI must not expose an `interviewer_id` picker for Milestone 2 and should treat direct `peer_to_peer` submissions as unsupported, routing Standard sessions through availability matching instead. `POST /api/interviews` stays AI-only; premium bookings are created only via the claim route (Story 7.15).
    - **Draft Storage (v1 → v2 migration/recovery)**: The legacy v1 draft key `mako:schedule-flow:draft:v1` lives in `sessionStorage` (pre-M7 location); the new v2 key `mako:schedule-flow:draft:v2` lives in **`localStorage`** so the durable draft survives browser/tab close. On restore, read the v2 `localStorage` key first; otherwise fall back to reading/validating the v1 `sessionStorage` key and import it — complete v1 AI/P2P drafts map to their unchanged `ai_direct`/`standard_p2p` branches (lossless for the valid normalized/restorable v1 state) and incomplete drafts (no submission branch yet) map to `pre_branch`; malformed/unknown/missing-`branch` envelopes are rejected and a v1 P2P draft is never reinterpreted as `verified_interviewer`. On write, always write v2 to `localStorage` first and only remove the v1 `sessionStorage` key after a successful v2 write (write-before-delete); an interrupted migration leaves v1 intact so a later restore retries read-v1 → write-v2 → remove-v1. The `verified_interviewer` branch persists exactly `{ slotId, idempotencyKey, startedAt }` (ISO-8601 `startedAt`) and is written synchronously and acknowledged **before** any claim request is sent — a failed/blocked persistence write prevents the claim request and leaves it unsubmitted for a clean retry.
    - **Booking Result**: A successful claim creates a `booking_channel = 'verified_interviewer'` (with `tier = 'premium'`) interview that appears in the scheduler's list/dashboard as a **normal participant interview** through the existing `GET /api/interviews` contract; join-time provisioning is unchanged. Scheduler-initiated cancellation or scheduler account deletion consumes the credit with no refund; interviewer cancellation or interviewer account deletion refunds exactly one credit (Story 7.14 outcomes). Claimed/cancelled slots are never shown as bookable, and no UI reopens or re-publishes a claimed slot.
    - **Scope Note**: Current Story 5 UI implementation scope is `system_design` type selection. Additional API-documented interview types remain forward-compatible contract surface for later UI expansion. The Verified Interviewer branch is the scheduler-facing booking surface and is distinct from the interviewer-facing `Interviewer Availability` publish/manage UI.
- **Interview Details (`/interviews/:id`)**: Comprehensive view of a specific interview's status and metadata.
    - **Implementation Status**: Core API route `GET /api/interviews/:id` is live and consumed by Interview Details, Interview Session, and Post-Interview Feedback pages. Session start/end/timer frontend controls are implemented on `/interviews/:id/session` through Story 3.11.
    - **Features**: Recording playback, whiteboard screenshots, feedback summary, and participant info.
    - **Data**: `GET /api/interviews/:id`
- **Interview Session (`/interviews/:id/session`)**: The immersive interview environment.
    - **Features**: Realtime Video/Audio, Shared Excalidraw Whiteboard, Session Timer.
    - **Data**: `GET /api/interviews/:id`, `POST /api/interviews/:id/provision` (returns `mode`, Realtime `realtime_session_id` + token, and Excalidraw `excalidraw_room_id` + `excalidraw_key`), `POST /api/interviews/:id/start`, `POST /api/interviews/:id/end`, `POST /api/interviews/:id/recording-consent`, `DELETE /api/interviews/:id/recording-consent`, `POST /api/interviews/:id/ai-chat` (**AI-led only**)
    - **Notes**:
      - Whiteboard integration is complete with Excalidraw collaboration (Stories 3.3/3.4). The session page renders the full whiteboard UI after provision.
      - Real-time media integration is complete with Cloudflare RealtimeKit (Story 3.6).
      - `peer_to_peer` sessions share one room/key pair across both participants.
      - `ai_led` sessions use a single-user room/key pair plus chat guidance.
      - AI chat guidance uses Excalidraw JSON snapshots as source-of-truth input; Mermaid is optional derived output for reporting/export.
      - **AI Coach Chat**: The AI-led (but not peer-to-peer) session renders an `AIChatSmart` panel that submits each user turn with the current Excalidraw canvas snapshot to `POST /api/interviews/:id/ai-chat`. The panel captures the canvas scene on-demand at submit time (not per-stroke), renders loading/success/failure states, and supports retry without a full session reload. Implemented via `apps/frontend/src/components/interviews/ai-chat/` and wired in `session-dumb.tsx` gated on `mode === 'ai_led'` through Story 4.4.
      - Lifecycle/timer UI must consume backend-backed interview status and workflow-backed timer state rather than local-only inferred countdown state.
      - `Start Session` / `End Session` controls are participant-scoped lifecycle actions, not whiteboard provisioning actions.
      - Session timer/start/end controls are owned by the dedicated lifecycle stories and routes, not by whiteboard provisioning or the details consumer rollout.
      - **Lifecycle control dependencies**: `POST /api/interviews/:id/start`, `POST /api/interviews/:id/end`. Timer fields `started_at`, `expires_at`, `warning_at` on `InterviewDetail`.
      - **Recording consent**: Participants explicitly allow or decline audio/video recording under consent copy `consent-copy-v1`; joining or starting never implies consent. The UI discloses transcript and AI feedback use, 30-day raw-recording retention, and that declining does not block the interview.
      - **Recording privacy and state**: The session shows only the current participant's choice returned by consent mutations plus the participant-safe overall `recording_status`. It never renders another participant's decision or readiness count, and locks consent controls once recording preparation begins or the interview ends.
      - **Retry safety**: Frontend retries of start/end are safe — backend guards transitions atomically and emits `start_requested`/`start_succeeded`/`end_requested`/`end_succeeded` lifecycle events with no sensitive data.
      - **State ownership**: Lifecycle controls and timer state derive from `useInterviewDetail` (TanStack Query); TanStack Store is reserved for local UI-only feedback such as lifecycle mutation errors. The countdown is derived from server-backed `expires_at`/`warning_at`, not stored as server state locally.
      - **Voice Wrapper Contract**: Voice is an ephemeral runtime wrapper only, scoped to `mode = 'ai_led'` sessions on this page. Speech-to-text is implemented (Story 4.10): microphone capture feeds recognized speech into the same chat input, which submits the same `message` field and full existing request contract to `POST /api/interviews/:id/ai-chat` with the same visible runtime states (idle/listening/transcribing/ready-to-send/failed). Text-to-speech playback of the `reply` field is not implemented and remains later scope (Story 4.11). Voice introduces no new backend route, no new request/response field, no persisted interview schema field, and no lifecycle state. Voice does not bypass or own `POST /api/interviews/:id/provision`, `POST /api/interviews/:id/start`, or `POST /api/interviews/:id/end`; those routes exclusively own provisioning and lifecycle boundaries.
- **Post-Interview Feedback (`/interviews/:id/feedback`)**: Detailed report and AI-driven insights.
    - **Features**: Performance scores (overall 0-100, communication/problem-solving/technical-depth dimensions), evidence-backed strengths, actionable improvements, transcript, and whiteboard captures.
    - **Data**: `GET /api/interviews/:id`, `GET /api/interviews/:id/feedback-status` (lightweight polling)
    - **Report States**:
      - **Unavailable**: `feedback_status = 'not_started'` with `feedback_unavailable_reason` (`no_consent`, `no_recording`, `unsupported_format`). Shows explanation copy; no retry action for users.
      - **Pending**: `feedback_status = 'pending'`. Shows "Feedback is queued for processing."
      - **Processing**: `feedback_status = 'processing'`. Shows "Feedback is being generated." Polls `GET /api/interviews/:id/feedback-status`.
      - **Failed**: `feedback_status = 'failed'` with `feedback_error_code`. Shows safe error message; no user-triggered retry (operational replay only).
      - **Ready**: `feedback_status = 'ready'`. Renders the full feedback v1 report (overall score, dimensions, strengths, improvements).
      - **Expired Raw Assets**: Recording/screenshots past 30-day retention. Feedback text and transcript remain available; raw asset playback returns availability status `expired`.
    - **Artifact Access**: Recordings and screenshots are accessed via participant-authorized application routes (`GET /api/interviews/:id/artifacts/recording`, `GET /api/interviews/:id/artifacts/screenshots/:captureId`), not direct R2 URLs.
